# Maintenance (lint) — wiki health check

Triggered by the phrases: "run maintenance", also "run lint", "check the wiki", "check integrity". The freshness trigger (when to offer a run proactively) lives in CLAUDE.md, §5 of "Discipline".

A periodic check. Two levels with different authority.

## Auto-fix (deterministic — Claude fixes on its own)

- Pages missing from `wiki/index.md` → add with a `(no summary)` stub.
- Index entries pointing at deleted files → mark `[MISSING]` (don't delete).
- Broken internal links with a single same-named file elsewhere → fix the path. In a `git worktree` working copy (the directories from `git rev-parse --git-dir` and `--git-common-dir` differ when compared as absolute paths), a link to a file git does not track (`git ls-files --error-unmatch` errors out) is checked against the main working copy (the first line of `git worktree list --porcelain`): the file is there — the link is not broken, don't fix it.
- `sources:` links to moved raw files with a single candidate → fix.
- Missing mutual links between obviously related pages → add.
- A top-level item in `archive/` or `output/archive/` (other than `index.md` itself and system clutter) that is absent from its archive's journal (the `index.md` next to it; no journal at all — don't create one) → append a line marked `[origin unknown]`: where it came from cannot be recovered, and the stub must show that rather than impersonate a complete journal.
- An item whose last line in the archive journal is "into archive" or `moved`, while it is missing on disk → mark that line `[MISSING]` (don't delete). Lines with outcome "deleted", `kept`, `returned`, `failed` are exempt — there is no item for them by construction.
- **Aged-out files in `output/` → `output/archive/`** — the "Moving into `output/archive/`" section below.
- **The completed buffer in `STATE.md`** ([state-rules.md](state-rules.md), rule 6; the class's section — "Completed last week", "Answered last week", or "Recently completed"). At the end of the pass, after the update check; not from a `git worktree` working copy. Delete the items whose date is older than `_Updated:_` by more than 7 days; more than ten dated items remain — keep the ten most recent and, under them, a single line "…and N more — removed YYYY-MM-DD" (update it at the next cleanup). An item is a list entry together with its sub-items; its date is the first one in it (a date in a file name or in a link doesn't count); a date without a year takes the year that brings it closest to `_Updated:_`. Don't delete, name instead: an item with no date, with an unchecked `- [ ]`, with something pending or a tail ("waiting for a reply", "by DD Mon", "still to do…") — judge by meaning, when in doubt don't delete. Lines with no date left over from the previous rule ("N tasks over the period…, see git log") — offer to remove; a "leave it" answer is recorded as for "Deferred items in STATE" below. Delete nothing and say so: there is no section with such a name; it holds no list (the `_empty_` mark is normal — stay silent); the `_Updated:_` line is not in the form the session-start check reads (the "Structure" item below), or its date is later than today. Don't change `_Updated:_` itself. In the report — the deleted items verbatim: without git they exist nowhere else; in the maintenance entry of `wiki/log.md` — their count.

## Report-only (heuristic — requires human judgment)

- Orphan pages with no incoming links.
- Concepts mentioned on several pages but lacking a page of their own.
- Stale statements contradicted by a newer source.
- ADRs with status `active` that contradict a newer ADR.
- Pages over 800 lines.
- Pages without a `sources:` field.
- **A role's slice has fallen behind.** For each role in `roles/` — domain pages that fall into its zone but lack its marking (tag/prefix): collect a proposal list and offer to tag them (the same init pass, [roles.md](roles.md) step 4); never mass-edit, markings go on with confirmation. Catches writes made outside the role chat or before the role existed; role writes are marked at intake (`roles.md`, "Saving"), this check is the backstop for what has accumulated.
- **Depth violation:** any `.md` in `wiki/<type>/<subdir>/...` (pages must sit flat in the type folder). Exceptions — `wiki/index.md` and `wiki/log.md`.
- **Folders in `output/`.** Top-level folders never move on their own — the "Folders" block of the "Moving into `output/archive/`" section below; a designated folder written into the tree with no folder on disk — name it.
- **Numbers issued twice** for principles and ADRs — the "Numbers issued twice" section below; for every duplicate — a ready split.
- **Temporary material in `tmp/` has been left lying around.** Any top-level item of `tmp/` — a run folder, a handoff file (`handoff-…`), a standalone file — older than 7 days → name them as a list with their age and offer cleanup **or a move into `archive/`**, if what is inside turns out to be not residue but a result worth keeping. A folder's age is that of the newest file inside it. `tmp/knowledge-check/` is the permanent log of the project-memory check, not residue: don't name it and don't remove it. A handoff to a new chat ([state-rules.md](state-rules.md)): work on it may still be going on — ask; its "Not yet saved to project memory" section still holds something the wiki doesn't have — offer to record that first. **Never delete them yourself, not even here:** normally the pass itself offers cleanup once the result has been accepted (`CLAUDE.md`, "A long pass"), while this check catches what never got that far or was left behind afterwards — the run was interrupted, the human moved on, the handoff was used up or never opened. Since the outcome is unknown, what's inside may be the only copy of what was done; hence a list and a question, nothing more. An empty `tmp/`, or none at all, is normal — stay silent.
- **Constructor files or `_to_delete/` left behind.** The root holds something from the scaffolding list (`base/`, `mechanics/`, `presets/`, `migrations/`, `START-HERE.md`, `ASSEMBLY.md`, `mechanics-catalog.md`, `README.md`, `CHANGELOG.md`, `versions.json`), and these are the constructor's files rather than the project's own files with the same names: `README.md` starts with `# knowledge-base-constructor`, `START-HERE.md` — with `# Start — assembling the project`, `versions.json` has a `base` key, `CHANGELOG.md` has `## base@` entries, `migrations/` holds `NNNN-*.md` files, `base/CLAUDE.md` contains `<<SLOT`, `ASSEMBLY.md` starts with `# Assembling a project from the constructor`, `mechanics-catalog.md` — with `# Constructor mechanics catalog`, `presets/` holds files whose first line is `# Preset manifest:`, `mechanics/` holds folders with `_about.md` → offer to remove them, with approval (in Claude Desktop — per the "Deletion when the environment blocks it" section below). A marker doesn't match, or in doubt — don't offer. The answer "leave it" — a dated line in `wiki/log.md`, and don't offer again until the human asks. There is a `_to_delete/` — remind them in one line that it can be dragged to the Trash. This check doesn't touch anything else in the root.
- **The project-memory check isn't working.** For yourself: fingerprint ≥ `base@43` and at least one of — `.claude/settings.json` (and `settings.local.json`) has no command with `judge.py` or `consent_nudge.py`; the files in `.claude/hooks/` are missing; `disableAllHooks: true` is set; `.claude/knowledge-check.off` exists. Tell the human that the project-memory check is not attached or is switched off — **always**, Claude Desktop included. Offer to attach it when the entries or files are missing: the files and entries from the mirror (`base/.claude/`), by steps 1–2 of migration 0004 (`migrations/0004-…` in the mirror; how to fetch files — step 2 of "Update check"); the write was refused by automatic mode — the section "Writing hooks when automatic mode blocks it". **Don't offer:** in Claude Desktop (project hooks don't work there — say they will work in Claude Code); with `disableAllHooks: true` (don't touch the flag); with no `claude` command — then don't offer `judge.py` at all, only `consent_nudge.py`, and say that checking my replies isn't available in this environment. `wiki/log.md` has `setup | hooks: not adding` — don't offer until the human asks; it has `setup | hooks: blocked by the environment` — offer again, but no sooner than 30 days after that date; a free-form line about an environment refusal written before `base@44` is not the answer "not adding". `.claude/knowledge-check.off` exists — say the check is off (on request, or by itself after failures); don't push to turn it on. `tmp/knowledge-check/log.txt` has `ERR` lines — say how many and the date of the last one: "on those days I may have missed offering to save something important".
- **Log dates not ascending:** an entry in `wiki/log.md` dated earlier than the previous one → report (the date was likely taken from a file mtime or from when the work was done, not from the environment). Don't sort automatically — whether to fix the date stamp or the entry position is the human's call.

### `STATE.md` hygiene (read silently every session → size = context tax)

`STATE.md` is read at the start of **every** chat, so its growth is a constant tax on context, and status drift distorts any answer to "what's in progress". Everything below is **report-only:** STATE holds intentions, and a false positive must not silently erase a plan (in STATE, maintenance itself only cleans the completed buffer — "Auto-fix"). The report explains WHY (one phrase about the file's purpose), not just "what". Thresholds are defaults; a large project may deliberately raise them (the numbers live here, in the rule's text).

- **Paragraph-line.** Any `STATE.md` line longer than **~2000 chars** is narrative: the details of a current item belong in the class's unit of work, those of a deferred one — in `BACKLOG.md`, and knowledge — in the wiki by its own routes (in STATE — a phrasing + a link, `state-rules.md` §5). Report: the top-N longest lines + their section. Catches the root cause before overall size does.
- **Size.** File > **~15 KB** or a single section > **~5 KB** (the completed buffer and the commitments calendar are not measured as a section) — report with the number and an estimate of how many tokens that is at each session start.
- **Deferred items in STATE.** Items with no due date that are not being worked on now and are not being taken up in the next two weeks ("after the release", "someday", "deferred", tech debt) → offer, as a list, to move them into `BACKLOG.md`; move on confirmation. Where to look: in the software and research classes — "In progress now", "Next", "Blockers and risks", and the domain 7th section if it holds more than a pointer line; in the business class — "This week" and "Next" (don't check "Open tracks", the commitments calendar, or what awaits the human's decision). An item whose due date has already passed — name it. What a due date is — `state-rules.md`, "`BACKLOG.md` — deferred items". The answer "leave it" — `## [YYYY-MM-DD] state | leave it: <item or section>` in `wiki/log.md`; ask again no sooner than 30 days later.
- **BACKLOG is waiting.** `BACKLOG.md` holds items awaiting the human's decision (the "Awaiting a decision" section or one close in meaning) — one line: how many and since what date the oldest one; in the business class — name them: they belong in STATE. An item with a due date in BACKLOG — name it: it belongs in STATE or the commitments calendar (the answer "leave it" — the same way).
- **Status drift inside STATE.** Items in "In progress" / "Next" carrying a completion marker (`✅`, `completed`, "CLOSED", "ACCEPTED") → should have moved to the completed buffer or disappeared. Report as a list.
- **Structure.** The class's section set (slot S5) in fixed order; empty ones marked `_empty_`; the `_Updated:_` field is a line of its own that starts with `_Updated: YYYY-MM-DD_`; a phrase inside the underscores, a space or a mark at the start of the line, a spelled-out date, the date after the closing `_` — name it: the session-start check does not read such a line and stays silent, as it would with a fresh STATE. _(Don't duplicate the "what to do if the date is stale" logic — the freshness trigger is already always-on in `CLAUDE.md`.)_
- **STATE ↔ wiki/code.** An item in STATE asserting a fact that contradicts a wiki page or the code (`state-rules.md` §7) → flag (don't edit: STATE is not canonical, but it's not the source of truth about facts either).

**Domain checks of the central type.** <<SLOT DOMAIN-LINT: a class with a central type adds its check here. Examples: `architecture/` pages missing the `implementation:` field or with broken paths in it (code drift, saas); a `claim` with status active/validated whose counter-evidence outweighs, and citations without a location (research); overdue commitments from the `STATE.md` "Commitments calendar" (business).>>

## Numbers issued twice

Parallel chats take "the next free" number at the same moment, and two different rules or decisions end up with one ID — a link to it leads to one of the two. Look at `wiki/decisions/` and `wiki/principles/`, outside code blocks.

**Principles.** A heading of any level that starts with `P-`; the ID follows the pattern `P-[A-Za-z]*\d+(\.\d+)*` (`P-A3` and `P-A3.1` are different). A heading with `P-` that doesn't fit the pattern (`P-PREFLIGHT-REPLAY`) — name it: not checked for repeats. An ID with a letter series (`P-D52`) is unique across the whole wiki. An ID with no series (`P-01`): a repeat within one file is a duplicate; a repeat across files — ask once whether the project numbers per file or across the wiki (the answer "per file" — `## [YYYY-MM-DD] numbers | per file` in `wiki/log.md`; stop comparing across files).

**ADRs.** The ID comes from the heading `# ADR-…` (up to a space or a dash); file names are not compared. Purely numeric ones are compared as numbers; a pair with a different digit count (`ADR-001` and `ADR-0001`) is named on a separate line — often these are old, different decisions. A `superseded` entry and its replacement under one ID are not a duplicate.

**The split — a ready one for every duplicate, applied on the human's confirmation.** The number stays with the side that has more links from documents that must not be edited (`raw/`, the archives, closed units of work, code); equal — the side with more links overall; equal again — the human chooses. The other side gets the next free number ([page-conventions.md](page-conventions.md), "ADR and principle numbers"). The proposal carries the list of links with the side each one belongs to; unclear ones are not edited but named; `wiki/log.md` and the uneditable are left alone.

**A note — on both sides.** A principle: on the one that stays — the line "Until YYYY-MM-DD this ID was also carried by the rule "…" — now P-…"; in the file of the renumbered one — a table "former ID (what it is about) → new" (if such a table exists, append to it). An ADR: in the one that stays — "Until YYYY-MM-DD this number was also carried by the decision "…" — now ADR-…", in the renumbered one — "Former number: ADR-… (issued twice, split on YYYY-MM-DD)", both right under the heading; rename the renumbered ADR's file. In `wiki/log.md` — `## [YYYY-MM-DD] numbers | split: <former> → <new>`; the answer "leave as is" — `numbers | leave it: <ID>`, don't offer again.

## Designated folders in `output/`

`output/` holds the project's documents and working results. **A designated folder** is a subfolder of `output/` in which the human told you to keep a certain kind of document ("keep contracts in `output/contracts`"). A one-off "put this in `output/X`" does not make the folder designated — just put the file there.

- **Set it up.** The human named a folder without a path — create it in `output/`. Write a line under `output/` in the "Architecture" tree of `CLAUDE.md`: `name/ (designated: what goes in)` — and in the same reply say what you remembered: "Contracts now go to `output/contracts`." The line didn't go in (the environment declined the edit) — say so at once and give the line so the human can write it in themselves: while the line is missing, the folder is not designated and the next chat will not know about it.
- **Use it.** Every next document of that kind goes there, without asking. Something sent from outside is processed as usual (the original — into `raw/`, [ingest.md](ingest.md)); a copy goes into the designated folder.
- **Not a designated folder:** a subfolder you created yourself for the files of one task — don't write it into the tree; a folder with code (a site, a landing page, scripts) — code lives in its own folder in the root, not in `output/`; a disposable subfolder declared by the class's lifecycle file.
- **The list of designated folders** is read from the tree in the `CLAUDE.md` file itself, not from memory.

## Moving into `output/archive/`

`output/archive/` is the archive for aged-out material from `output/`; its journal is `output/archive/index.md`. **Maintenance moves files on its own; folders — only on the human's answer.** A move loses nothing: the file stays on disk, only its folder changes. Maintenance deletes nothing from `output/` — deletion happens only on the human's direct request about named files.

**When.** At the end of the pass, after the update check. Not done from a `git worktree` working copy and not without a human on the line (a schedule, `-p`, a subagent) — only name the candidates.

**The first time, and the switch.** As long as `wiki/log.md` has neither a `move | on` line nor a `move | name only` line — show how many files would move and the list (up to the 20 oldest, the rest as a count) and ask, as a separate question, whether to move them. A "yes" to that very question — record `## [YYYY-MM-DD] move | on` and move; from then on — without asking. Don't take a general "yes" to several questions at once as consent — ask again. No answer or "not now" — don't move, ask at the next maintenance. "Don't move" — at any moment, outside maintenance too — the line `move | name only`: with it, name the candidates and leave them alone until the human asks to move again (then — `move | on`). The later of the two lines applies.

**What moves on its own.** A top-level file of `output/` unchanged for **more than 30 days**, and a top-level file, just as old, of a disposable subfolder declared by the class's lifecycle file (in the business class — `output/drafts/`); folders inside it are asked about like any others (the "Folders" block). The time is the later of the modification time and the time the item appeared in place (`mtime` and `ctime`): otherwise a file unpacked or copied with an old date would leave on the day it arrived. Don't follow symbolic links. Limits — say so if you see them: on Windows a file moved within a drive keeps both times old; after the project is relocated or cloned (possibly on a connected folder in Claude Desktop too — not verified), all files share one recent time — on a non-empty `output/` call "everything is fresh" a reset dating instead of reporting "clean".

**Doesn't move, silently:** dotfiles and system clutter (`.gitkeep`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, `~$*`), `output/archive/` itself, a file whose last line in the archive journal is `kept` (in `archive/index.md` from the previous rules such an outcome holds for 30 days from its date).

**Doesn't move — and enters the report as a count per reason:**
- **the file is linked from somewhere in the project** — anywhere except: `wiki/` and `BACKLOG.md` (the link gets fixed there), the completed buffer in `STATE.md`, closed units of work (a `completed` spec), the archives, `raw/`, `_to_delete/`, maintenance's own reports and journals, and files that are themselves moving. A link from `STATE.md`, an unclosed unit of work, a handoff or a journal in `tmp/`, code, CI, `roles/`, `CLAUDE.md`, `methodology/`, a file in `output/` that stays — protects it; a candidate that ends up staying protects too — check once more after the first selection. A question number `Q-NNN` in STATE (outside the buffer) protects `output/q-NNN-*`;
- **code reads `output/` by a pattern** (`glob`, reading the folder, a name assembled from parts — dates, numbers) that the file matches;
- **the file itself is a program** (`.py`, `.sh`, `.js`, `.command`, `.ipynb`, and the like): in a new place its paths would break;
- **under git the file is hidden by a `.gitignore` line for its own path and would not be hidden in the archive** (`git check-ignore -q` matches the old path and does not match the new one): the move would bring it under git;
- **the name is taken in the archive** (check before the move, case-insensitively: `mv` would otherwise put a folder inside its namesake) — for the human to decide: leave it in place (a `kept` line) or rename it first.

**Procedure.**
1. **Links.** Search in one pass over the list of candidate names across the whole project, including what is hidden and what git ignores: `rg --no-ignore --hidden -g '!.git'` (the ordinary search, and `grep` in Claude Code, silently skip those). Compare after normalizing to one Unicode form (NFC) and decoding `%20` and the like, case-insensitively. What the search cannot see — say it: links without a name or without an extension, mentions and links inside `.docx`/`.xlsx`/`.pptx`, other branches and working copies, bookmarks and emails outside the project.
2. **The archive.** The `output/archive/` folder exists but holds no journal — it is not ours: ask whether to put things there too (then start a journal) or not to move (`move | name only`). Under git: `git check-ignore -q output/archive/x` matches while `git check-ignore -q output/x` does not (usually because of an `archive/` line with no leading slash) — neither git nor the ordinary search will see the archive and its journal: tell the human and offer to add the line `!/output/archive/` to `.gitignore` (leave the `archive/` line itself as it is). Don't move until they answer; "no need" — move as is.
3. **One item at a time: journal line → move → check.** The journal is `output/archive/index.md`: the header `# output/ archive journal` and the table `| date | what | from | outcome |`, outcome `moved`; it is not a wiki page (no frontmatter, outside ingest). The move — without renaming and without copying: what git tracks (`git ls-files --error-unmatch <path>` succeeds) — `git mv`, the rest — `mv -n`. The check — the item is gone from the old place and present in the archive; still there (the file is open or busy) — change the outcome in its line to `failed: <reason>` and go on. A refusal by the environment of the action itself (permission mode, folder rights) stops the move altogether — change the outcome the same way, name the rest.
4. **Links** to what was moved are fixed in `wiki/` (including `sources:`) and `BACKLOG.md`; don't touch `wiki/log.md`. Links from closed units of work and `raw/` are not fixed — the file is found by its name in `output/archive/`. The contents of moved files are not edited: relative links inside them may stop opening.
5. **Under git** — if there was at least one `git mv`: add the journal to the index (`git add output/archive/index.md`; git ignores it — skip) and make one commit of your own tracked paths only — the old and new paths of what went through `git mv`, the journal, the files with fixed links: `git commit -m "lint: move into output/archive/ (N)" -- <paths>`. A file that, besides the fixed link, carries someone else's uncommitted edits is left out of the commit. The commit failed — don't work around it: tell the human that the renames are left in the index.
6. **Report:** "checked N files, moved M" and the names of the moved ones — up to the 20 oldest, the rest as a count, the full list is in the journal; not moved — a count per reason, names only where an answer is needed (a taken name). Something that came from outside (a file someone filled in, material that was sent) moves like everything else — offer to transfer it from the archive into `raw/`. Moved 0 — say so, with the number checked: silence is indistinguishable from a broken check.

**Folders.** Top-level subfolders of `output/` — designated ones and any others, except `archive/` and the class's disposable subfolder — and folders inside the disposable subfolder never move on their own. A folder in which nothing has changed for more than 30 days (by the newest file inside, at any depth, by the same time count; system clutter doesn't count; an empty one — by its own time) goes into one question covering all such folders: "Nothing has changed in these folders for a month. Which ones should go to the archive, which should stay, which are designated folders for documents (tell me what goes in), and which should I stop asking about?" The list holds up to 20, the rest as a count; for each one name who links to it (a role, a rule, a document) — the human's answer decides. Don't ask about a folder a program reads (a path in code, scripts, CI, `data/`), or about a folder whose contents `STATE.md` (outside the buffer) or an unclosed unit of work links to. Having asked, record in `wiki/log.md` one line `## [YYYY-MM-DD] folders | asked: <name>, <name>`; the answer gets a line of its own; the folder name — as on disk, without `output/`; the last line about a folder applies:
- "archive" → move it whole by the same procedure and with the same checks (a taken name, a `.gitignore` line for its path); one line in the journal; it was a designated folder — remove its line from the tree;
- "leave it" → `folders | leave it: <name>`; after it, and after "asked" with no answer — ask again no sooner than 30 days later;
- "stop asking" → `folders | permanent: <name>` — don't ask until the human asks you to (`folders | ask again: <name>`);
- "it's a designated folder" → set it up (the "Designated folders in `output/`" section) and record "leave it".

**Bringing something back from the archive.** Move it back (don't copy), journal outcome `returned`; under git — per step 5. On the human's request ("bring it back", "leave this file alone") — add a `kept` line as well: without it the file would leave again in a month; it is lifted by the human's request — with a `lifted` line. When we take up work whose working file is in the archive — bring it back without `kept`: the link from STATE keeps it alive. The human asks to sort out `output/` now — move what they named by the same procedure, without waiting for 30 days.

**Also worth knowing.** In the archive an item lies under its own name (a folder — whole); the archive is read from, its contents are not edited. The archive was inherited from the project's previous rules (a journal in another form, folders inside) — don't re-sort it and don't rewrite the journal: append new lines as a table at its end.

## Retiring into `archive/`

`archive/` is for **material we generated that has aged out**: things that settled in `tmp/`, lost their relevance, but are not worth deleting outright (`output/` has an archive and a procedure of its own, the section above). It is a different dimension from `raw/`: that one holds the **primary sources** we compile the wiki from, and they are immutable (in a conflict with the wiki, the source wins).

**The human decides, not the check.** Claude collects candidates, shows what it knows about each, and gives a one-line recommendation — but the human picks the outcome. Computing the outcome on its own was tested against live data and does not work: most items simply lack the signal it would need.

**For each candidate show:** what it is (name, type, age), who links to it, and the recommendation. Then one of three outcomes, each **item by item and confirmed**; a blanket "yes, sort it all out" is not accepted — the working layer may have no second copy.

1. **Into `archive/`** — aged out, but throwing it away would hurt: it went outside, it is the only copy, it may have to be produced later. **Function decides, not extension**: a question that went to a person as `.md` is as much a record as a `.docx`.
2. **Delete** — the knowledge is already in the wiki (name the page) or the result is reproducible (name the script or command). Can name neither — this is not outcome 2.
3. **Keep** — the work is alive. Recorded with a date and **not shown again before the next threshold**, otherwise the list never shrinks and people stop reading it.

**What the link search does not see** — say it out loud instead of passing it off as a clean result: pattern-based access (`glob`, `rglob`, reading a whole folder), links without a file name ("the artifact is in `output/`"), mentions inside `.docx`/`.xlsx`/`.pptx`. An unreadable format is **not** "no links". Exclude `wiki/log.md` and `wiki/index.md` from the search area: a journal and a catalogue mention everything that ever went through ingest, and would shield everything. Exclude `_to_delete/` too: it holds what has already been decided to throw away.

**Special cases.** A folder older than the threshold — open one level and sort its items, don't move it wholesale. Something that came from outside (a file someone filled in, material that was sent) is not our artifact but a primary source: offer `raw/`, not the archive. A same-stem neighbour (`X` and `X.zip`, `X` and `X_v2`) — call it out as a pair regardless of age and ask which version is the real one.

**Archive rules.**
- Flat, no state subfolders. Don't rename files — renaming breaks the links that still point at them.
- **Secrets and personal data** — check and strip them **before** the move, by the same rule as on the way into `raw/` ([ingest.md](ingest.md)).
- **`archive/index.md` is a retirement journal, not a wiki page** (no frontmatter, outside ingest and outside `page-conventions.md`). One line per outcome, deletions included: `| date | what | from | outcome | closed by (wiki page / command) |`. The line is written **before** the action: otherwise deleting is cheaper than archiving, and cheaper here means more irreversible.
- The archive is read from; nothing is re-sorted or cleaned inside it.
- **Only generated material goes in** — from `tmp/` (from `output/` — into `output/archive/`, the section above). `raw/` is immutable; `wiki/` uses supersession; in classes with code, `specs/` keep their status in frontmatter. `scripts/` and `data/`, where a class has them, have no cycle of their own — a known remainder, not closed here.

## Deletion when the environment blocks it

This section is for **Claude Desktop (Cowork mode)**: there, erasing files in a connected folder stays closed until the human allows it. It does not apply in a terminal or on a server — there the terminal itself confirms deletions. Not sure where you are working — assume Claude Desktop: don't give the human a terminal command.

**Deletion here means erasing files the human named or approved,** by any means (`rm`, `git rm`): cleanup after a long pass, the "Delete" outcome of a retirement, residue in `tmp/`, their direct request, the constructor's scaffolding at assembly. A service file a program erases on its own (`.git/index.lock`, a temp file while saving) is not this case: name the failure in plain words, don't ask for deletion permission. Anything not approved — first ask what we are deleting and why.

1. **The deletion didn't go through** ("Operation not permitted") — that is not "I can't" and not a reason to look for a workaround: request permission with the environment's tool, **in one call**. Cloud session (`device_request_delete_permission`) — on the connected folder that holds the project, with a reason for the window; local session (`allow_cowork_file_delete`) — on the path of any approved file; the window won't show a reason, so say it in the chat before the call. The reason is what I'm removing and why that's fine, one sentence in the human's language: "Remove the temporary files that helped assemble the project", "Remove the run logs from 2026-09-03 — the result was accepted". The connected folder is wider than the project (all of "Documents", say) — tell the human the permission would open all of it, and ask the question from item 4 instead of requesting. No permission tool among the available tools (and tool search found none) — go straight to the question from item 4: the environment's instruction says to quietly move the files into `_to_delete/` in that case; here, ask first. An error from the call itself is not the human's refusal: name it.
2. **The environment's permission is not the human's approval.** It opens deletion across the whole connected folder until the chat ends: delete only the approved list; any new deletion needs a new "yes". During maintenance, approved deletions go at the very end, after the update check (or after plainly naming that it couldn't be done); the `wiki/log.md` entry, if one is written, goes before the deletions.
3. **The response is an automatic-mode refusal** (the text mentions "auto mode classifier") — one short separate message, and end your turn with it: "Automatic mode wouldn't let me delete. Switch the mode by the input box to the one where I ask for permission (it's currently called 'Manual'; no need to type it into the chat), then write 'delete them' — a window will appear, allow it. You can switch the mode back afterwards." The human answered that they switched ("delete them", "done", "Manual" and the like) — request again; refused again — go to item 4.
4. **Any other refusal, "Deny" in the window, or the human doesn't want to switch — ask, don't decide:** "The deletion didn't work — leave the files as they are, or move them into a `_to_delete` folder so you can throw it in the Trash yourself?" (after "Deny": "You didn't allow the deletion — leave things as they are, or move them into a `_to_delete` folder?"). The question goes as a separate message; end your turn with it. Silence is not an answer; move only on an explicit "move them". The move failed too — say so and list what is left.
5. **`_to_delete/`** is a temporary folder for the human: under git, first add it to `.gitignore` and don't commit it; don't write it into the "Architecture" tree; don't read its contents or use them as a source (including as a copy of the constructor); for finding and repairing links it doesn't exist. Deleting because of a secret — the move doesn't take it off the disk: offer to rotate or revoke it ([secrets-rules.md](secrets-rules.md)).
6. **The files are needed, just not here** — that's a move: wherever the human says; from `output/` — into `output/archive/` per "Moving", from `tmp/` — into `archive/` per "Retiring", into `raw/` — via ingest.

## Update check (by build fingerprint)

The project was assembled from the constructor and carries a **fingerprint** on line 3 of `CLAUDE.md`: which part versions it was assembled from (`base@N · <mechanics>@N · <manifest>@N`).

**This block is UNCONDITIONAL: it runs in full on EVERY lint run, regardless of the wiki's state.** Whether the wiki is empty, freshly bootstrapped, unchanged since last time, the N-th lint in a row, health is clean — none of that enters the condition AT ALL: upstream (the constructor) evolves independently of your wiki. Excuses like "nothing changed", "can skip it", "already checked", "same wiki" are forbidden; that is precisely the failure this block was made mandatory against.

**Without two artifacts the check is NOT done** — don't state an update verdict and don't append to `wiki/log.md` until your reply contains: (a) the pasted body of the `versions.json` response; (b) a per-part comparison table with the numbers. "Re-checked, no updates" without them is an empty claim, not a result.

1. **Read your own fingerprint** (line 3 of `CLAUDE.md`) — the `part@version` list.
2. **Fetch fresh versions with a live read (not from memory / a previous output) and PASTE its output into the reply. Only pinned to a commit (SHA), never the `main` branch.** If the shell has network — two steps:
   ```bash
   SHA=$(git ls-remote https://github.com/DanilZherebtsov/knowledge-base-constructor-en.git HEAD | cut -f1)
   curl -s "https://raw.githubusercontent.com/DanilZherebtsov/knowledge-base-constructor-en/$SHA/versions.json"
   ```
   **Shell without network (sandbox) — the same two steps via `WebFetch`** (a live GET that bypasses the local sandbox, so it works where `curl` is blocked): first `https://api.github.com/repos/DanilZherebtsov/knowledge-base-constructor-en/commits/main` → take the `sha` field; then `WebFetch` the raw URL with that SHA in the path.
   **Why by SHA and not by `main`:** `raw/main`, the contents API, and the `WebFetch` cache are all edge caches; reads of a mutable branch diverge, and there is no way to pick the right one (real cases: the contents API returned 12, raw returned 8, the truth was 14). A URL with the SHA in the path is **content-addressed** — no cache can return foreign bytes under that SHA; the snapshot is coherent and current, and the "which read to trust" divergence disappears by construction. A slightly stale SHA is fine — it yields a coherent snapshot, not a mix of numbers from different caches.
   **`WebSearch` is FORBIDDEN for this check.** The search index serves a days-old snapshot — it is what produced a phantom `base:12` against a fresh upstream. Only a live GET: `curl` or `WebFetch`.
   **The "upstream" number counts ONLY if it arrived via a SHA-verified live read.** Neither the shell nor `WebFetch` worked — the check is NOT done: say exactly that ("couldn't reliably check upstream"); do NOT put a number from cache/search/memory into the table, and do not output a "matches" verdict.
3. **Compare per part and show the table** `part | mine | upstream | verdict`. Upstream above mine → that part has an update. Parts the project does NOT carry (mechanics not baked in) — ignore.
  - **Exception — an unwired part the update exists for.** If the entry of an updated part references a mechanic the project does not have, do not drop it silently: name it to the human **as an offer** ("this capability now exists, shall I wire it in?"); they agreed — attach it per the "Attach a capability the project doesn't have" section below. Otherwise they get "some catchers were added" with no explanation of what the catchers are for, and never learn about the update most useful to them. The verdict "no updates" is allowed ONLY if in the shown table every part has `mine == upstream`. Only part versions are compared, never whole files — cosmetics and instance content stay out of the comparison.
4. **For each updated part — figure it out yourself** (an internal assessment, not output for the human): read its entry in the upstream `CHANGELOG.md` — **a single file in the mirror root**, heading `## <part>@<version>` (e.g. `## base@19`, `## spec-lifecycle@2`). Read it **at the same SHA pin as step 2** (the same commit) — the version and its description come from one snapshot, ruling out the "number newer than description" cache skew. For a class manifest — the content of `presets/<class>.md`. Classify the blast radius: *`[instruction]`* (prose/rule) — fixed by file edits, knowledge (`wiki/`) untouched; *`[format]`* (a new field/section on pages) — requires a `wiki/` migration.
5. **Report to the human — in plain language, no IT jargon.** The changelog is written for a developer — don't retell it verbatim; translate it into substance. For each updated part the human must understand three things:
   - **What changed** — 1–2 sentences in terms of benefit, not mechanics.
   - **Does it affect them** — either "nothing to touch, this is about how I work" (`[instruction]`), or "your notes will gain <what exactly> — can be filled in gradually" (`[format]`).
   - **Take it or not** — a one-sentence recommendation.

   In the reply to the human do NOT use: "fingerprint / version / base@N / mechanic / manifest / migration / lazy-eager-skip / `[format]`-`[instruction]` / blast radius / API".
   > ✗ Jargon: "base@12: `[instruction]` Flow B now goes through the contents API, raw cache eliminated, no migration needed."
   > ✓ Human: "I picked up an improvement to how I check for updates: I sometimes compared against a slightly stale list and could miss a fresh update — now I always look at the most current one. Doesn't touch your notes, nothing to do. I'd take it — it's simply more reliable."

   Then **offer to apply**: `[instruction]` — surgically, with confirmation; `[format]` — name the scope in human terms ("a field will be added to roughly N notes") and the choice: **(a)** fill in as we go, whenever we open a note — the default; **(b)** sweep through all of them now; **(c)** postpone. Never mass-rewrite notes without consent. Applied — **bump that part's version in the fingerprint** (line 3).

After lint — append to `wiki/log.md`:
```
## [YYYY-MM-DD] lint | found N issues, fixed M
```
