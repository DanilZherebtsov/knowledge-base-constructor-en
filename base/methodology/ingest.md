# Ingest — adding new knowledge

Triggered by phrases: "process this document", "remember this", "capture this", "add to the wiki". Knowledge that comes not from a file but from the conversation itself — the "Knowledge from the conversation" section below.

When the human throws files into `input/` (the drop zone for incoming materials), points to a source, or puts a file into `raw/`:

1. **Read the source.** If it is long (multi-page material, a long transcript) — read it in parts, don't skim. First discuss the key takeaways and confirm intent before changing the wiki.
2. **Recognize the input and place it — layout is Claude's job, not the human's.** Before placing anything, recognize what it is: **working source code** (a code tree, a deployable site, scripts, a project with a build/manifest) or **regular material** (a document, a transcript, data, someone else's code sample for study)?
   - **Working code** — do NOT bury it in `raw/`. Ask the human in plain words: "is this code you'll maintain and develop here, or someone else's example to study?". If **we own / change / deploy it** → the code lives in a **root folder named for what it is** (`landing/`, `src/`, `scripts/`), created by the human's decision; **not** `raw/` and **not** `output/`. The files on disk are the source of truth; only knowledge about the code goes into the wiki (what it is, key facts — the offer, pricing, operations), never the code itself. **The code arrived ready-made — the wiki has no knowledge of it yet:** before the first task on it, offer a reconnaissance pass (describe the modules and contracts into the wiki, a page per module), otherwise the task-statement review will read emptiness and silently return "clean". <<SLOT OWNED-CODE: with the `software-engineering` mechanic active — replace with: "code-folder layout, code-ownership conventions, the execution cycle, and role suggestions are governed by [software-engineering.md](software-engineering.md)". In plain base without the mechanic — keep: "if the project seriously starts owning code, suggest that the human attach the `software-engineering` mechanic; the attach procedure — [lint.md](lint.md), the "Attach a capability the project doesn't have" section".>> If the human says "it's an example to study" — proceed as with regular material.
   - **Incoming brand identity** (a logo, brand book, guidelines, mockups, a finished deck, brand fonts) — do not bury it in `raw/` silently. Ask in plain words: **"is this our style, the one we make everything by from now on — or someone else's example for inspiration?"**. "Ours" → the values are carried into `BRAND.md` (a root file the human edits), the source file is placed next to it and remains the source of truth; only the fact and the decision go into the wiki, never a retelling of the guidelines. "An example" → a reference with no obligations, then proceed as with regular material. <<SLOT OWNED-DESIGN: with the `design` mechanic active — replace with: "handling incoming brand identity, carrying it into `BRAND.md`, and all further work on visual things is run by [design.md](design.md)". In plain base without the mechanic — keep: "if the project seriously starts producing visual things, suggest attaching the `design` mechanic; the attach procedure — [lint.md](lint.md), the "Attach a capability the project doesn't have" section".>>
   - **Regular material** — move the source from `input/` (or from wherever indicated) into a fitting `raw/` subfolder, `raw/<concern>/YYYY-MM-DD-slug.md`; if none fits — create a new one and add it to the `CLAUDE.md` tree (the "Structure grows as needed" rule). `raw/` subfolders are never created in advance: they appear here, when material actually arrives. Name a new one from the class's vocabulary if the material fits it — that keeps the layout uniform: <<SLOT RAW-DEFAULTS: the class's vocabulary of `raw/` subfolder names; default — by the material's concern, catch-all `misc/`>>. The human never needs to know the `raw/` subfolders — they throw things into `input/`. Preserve the original. **Strip secrets** (passwords, keys, unnecessary personal data). Add a metadata header: source (URL, if any), date received, publication/document date (if known), authors. After placement `input/` is empty (files moved into `raw/`).
3. **Compile into the wiki.** The unit of knowledge is <<SLOT KNOWLEDGE-UNIT: a page (default) | a `claim` for research>>. For each affected unit:
   - **Same thesis** → merge, add the source to `sources:`, update point-wise. If the claim was marked `[per the human, not confirmed by a document]` or `[Claude's inference, unverified]` and the new source confirms it — remove the mark.
   - **New concept** → a new page in the fitting type folder, named for the concept (not for the file name). For types with prefix grouping — use the prefix. Type choice and format — [page-conventions.md](page-conventions.md).
   - **Contradiction** → annotate the conflict in the text, present both sides, escalate to the human for resolution. Never pick a side silently.
   - **Working as a role** (`roles/<role>.md` is open) → the page gets the role's slice marking: the name prefix on a new page, the role's tag in `tags:` — both on a new page and on the one appended to (no tag → add it). Without the marking the finding drops out of the role's slice for good: marking at role creation is one-off, while writes keep coming. Mechanics — [roles.md](roles.md).
4. **Cascade.** Scan the same type folder and the index for materially affected pages. Update them, refresh `updated:`.
5. **Update `wiki/index.md`** — entries for the affected pages. Format — [index-log-format.md](index-log-format.md).
6. **Append to `wiki/log.md`:**
   ```
   ## [YYYY-MM-DD] ingest | <name of the main page>
   - Updated: <cascade-updated page>
   ```
7. **Commit — if the project is under git.** One commit, message `ingest: <source>`. Without git the step is skipped (history lives in `log.md` and page dates).

An important rule: **when updating any claim — reread the raw source it references.** Do not treat the wiki text as the primary source — that is how drift creeps in.

**A big source** (an hour-plus interview, a detailed report): don't extract everything in one pass — 3–5 key points per ingest, mark the rest right in the raw file ("min. 45:00: about X — to review") and come back later.

## Knowledge from the conversation (no document)

The input is not a file but what came out in the conversation: under the "Request resolved" rule in `CLAUDE.md` or on a direct "remember this". The offer line and "yes, save it" are the understanding check; a direct request to record ("remember this", "save it to memory") is already consent (except for third parties' personal data); the human telling you what they themselves are writing down or dictating is not. One or two findings are an isolated addition: the understanding check is the offer line itself plus the "yes", the independent review does not switch on; an ADR or a contradiction with the wiki — by the usual measure of risk. `sources:` is mandatory here too. The order:

1. **The human's confirmation — before any write**, including `raw/`: nothing is ever deleted there. Third parties' personal data (phone numbers, addresses) — only if the human said "yes" to exactly that.
2. **One note per conversation:** `raw/from-chat/YYYY-MM-DD-<topic>.md` — the only file in `raw/` holding the words of our chat. Not to be confused with meeting transcripts (the class has its own folder for those): there it is someone else's speech in full, here it is an excerpt from our chat. Create the subfolder on the first write and add it to the `CLAUDE.md` tree. Header — the date of the first entry, who took part, what the conversation was about. Each finding is an item `## N. <short>`; the next confirmed one in the same conversation is a new item at the end, what is written is not edited (a correction is a new item referring to the old one). In an item:
   - **the human's words** (their decision, their correction, a fact only they know) — **verbatim**, from the current conversation; after context compaction they are gone — mark it "paraphrase" or ask them to repeat, never make up a quote;
   - **Claude's own inference** (a cause it found, a format it read) — only with a snapshot of the evidence (command output, a piece of the file); without a snapshot — with the mark `[Claude's inference, unverified]`, both in the note and on the page;
   - **anything impermanent** (command output, a service response, a web page, a file from `output/`) — a snapshot of the relevant piece: a month from now it can't be re-read. A direct link without a snapshot — only for files in `raw/` and code files with a commit (`path@<commit>`; without git — a snapshot).

   **A secret is not a finding** ([secrets-rules.md](secrets-rules.md)): the note gets only the variable name and where it lives; if the value appeared in the chat — say the access is exposed and offer to rotate it. Check command output for tokens and connection strings before writing.
3. **Then — as for regular material: from "Compile into the wiki" through "Commit" inclusive.** The source is `[raw/from-chat/<file>.md, item N]`; a principle's "Source" field points there too. A fact about the world from the human's words, not checked against a document, gets the line `[per the human, not confirmed by a document]` right after the claim (their decision and correction are not facts about the world — no mark needed). Commit — `ingest: conversation YYYY-MM-DD — <topic>, item N`, files by path (`wiki/`, `raw/from-chat/`), not everything at once.
