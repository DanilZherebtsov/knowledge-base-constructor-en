# Maintenance (lint) — wiki health check

Triggered by the phrases: "run maintenance", also "run lint", "check the wiki", "check integrity". The freshness trigger (when to offer a run proactively) lives in AGENTS.md, §5 of "Discipline".

A periodic check. Two levels with different authority.

**An unfinished move — first.** There is a sign of step 0 of "Update check" (a move to a new first digit is not finished) — start the pass with it. The items that compare the constructor's files with the mirror ("The project's checks aren't working", "The `raw/` guard is not in place", "Reply style not enabled") are not run in this pass — the move itself puts them in order; the rest — after it.

**Knowledge unchanged — don't check it.** Condition: `wiki/log.md` has a `lint` entry, no entries follow the last one except `update`, `setup`, `folders`, `move`, `state`, and `find wiki raw ! -path wiki ! -path wiki/log.md ! -path '*/.*' -cnewer wiki/log.md` from the project root printed nothing (another entry, any output, a command error or no shell — a normal run). Run the command on every run: reading the log doesn't replace it. When the condition holds:

- **The last `lint` is from today or later** — do only the "Update check" and reply: "Maintenance already ran today and the entries in the project memory haven't changed since — no point repeating it. Need it again — say 'run maintenance anyway'." Then — whether there are updates, with the proofs of the "Update check"; one line on what is waiting for the human's answer, if the log shows it. Don't add a `lint` entry; update accepted — `## [YYYY-MM-DD] update | to X.Y.Z`; only the number raised — the line from step 4a.
- **The last `lint` is from yesterday or earlier** — run with no warning, but without checks of the wiki pages themselves: the index, links and mutual links, `sources:`, orphans, concepts without a page, contradictions and stale statements, page size and depth, role slices, numbers issued twice, domain checks of pages, except those that depend on the date or on files outside the wiki (like "Code and `architecture/`"). Everything else — as usual, even if it looks into the wiki. In the report — "The entries in the project memory haven't changed since the last maintenance, I didn't re-check them. Need it — say 'run maintenance anyway'."; the entry heading — `## [YYYY-MM-DD] lint | knowledge not checked; found N issues, fixed M`.

The human insists ("run maintenance anyway", "do it anyway") or asks to check the wiki or integrity — a full run.

## Auto-fix (deterministic — the agent fixes on its own)

- Pages missing from `wiki/index.md` → add with a `(no summary)` stub.
- Index entries pointing at deleted files → mark `[MISSING]` (don't delete).
- Broken internal links with a single same-named file elsewhere → fix the path. In a `git worktree` working copy (the directories from `git rev-parse --git-dir` and `--git-common-dir` differ when compared as absolute paths), a link to a file git does not track (`git ls-files --error-unmatch` errors out) is checked against the main working copy (the first line of `git worktree list --porcelain`): the file is there — the link is not broken, don't fix it.
- `sources:` links to moved raw files with a single candidate → fix.
- Missing mutual links between obviously related pages → add.
- A top-level item in `archive/` or `output/archive/` (other than `index.md` itself and system clutter) that is absent from its archive's journal (the `index.md` next to it; no journal at all — don't create one) → append a line marked `[origin unknown]`: where it came from cannot be recovered, and the stub must show that rather than impersonate a complete journal.
- An item whose last line in the archive journal is "into archive" or `moved`, while it is missing on disk → mark that line `[MISSING]` (don't delete). Lines with outcome "deleted", `kept`, `returned`, `failed` are exempt — there is no item for them by construction.
- **Aged-out files in `output/` → `output/archive/`** — the "Moving into `output/archive/`" section below.
- **The completed buffer in `STATE.md`** ([state-rules.md](state-rules.md), rule 6; the "Recently completed" section). At the end of the pass, after the update check; not from a `git worktree` working copy. Delete the items whose date is older than `_Updated:_` by more than 7 days; more than ten dated items remain — keep the ten most recent and, under them, a single line "…and N more — removed YYYY-MM-DD" (update it at the next cleanup). An item is a list entry together with its sub-items; its date is the first one in it (a date in a file name or in a link doesn't count); a date without a year takes the year that brings it closest to `_Updated:_`. Don't delete, name instead: an item with no date, with an unchecked `- [ ]`, with something pending or a tail ("waiting for a reply", "by DD Mon", "still to do…") — judge by meaning, when in doubt don't delete. Lines with no date left over from the previous rule ("N tasks over the period…, see git log") — offer to remove; a "leave it" answer is recorded as for "Deferred items in STATE" below. Delete nothing and say so: there is no section with such a name; it holds no list (the `_empty_` mark is normal — stay silent); the `_Updated:_` line is not in the form the session-start check reads (the "Structure" item below), or its date is later than today. Don't change `_Updated:_` itself. In the report — the deleted items verbatim: without git they exist nowhere else; in the maintenance entry of `wiki/log.md` — their count.

## Report-only (heuristic — requires human judgment)

- Orphan pages with no incoming links.
- Concepts mentioned on several pages but lacking a page of their own.
- Stale statements contradicted by a newer source.
- ADRs with status `active` that contradict a newer ADR.
- Pages over 800 lines.
- Pages without a `sources:` field.
- **A role's slice has fallen behind.** For each role in `roles/` — domain pages that fall into its zone but lack its marking (tag/prefix): collect a proposal list and offer to tag them (the same init pass, [roles.md](roles.md) step 4); never mass-edit, markings go on with confirmation. Catches writes made outside the role chat or before the role existed; role writes are marked at intake (`roles.md`, "Saving"), this check is the backstop for what has accumulated.
- **Depth violation:** any `.md` in `wiki/<type>/<subdir>/...` (pages must sit flat in the type folder). Exceptions — `wiki/index.md` and `wiki/log.md`.
- **Folders in `output/`.** Top-level folders never move on their own — the "Folders" block of the "Moving into `output/archive/`" section below; a designated folder written into the tree with no folder on disk — name it.
- **Numbers issued twice** for principles and ADRs — the "Numbers issued twice" section below; for every duplicate — a ready split.
- **Temporary material in `tmp/` has been left lying around.** Any top-level item of `tmp/` — a run folder, a handoff file (`handoff-…`), a standalone file — older than 7 days → name them as a list with their age and offer cleanup **or a move into `archive/`**, if what is inside turns out to be not residue but a result worth keeping. A folder's age is that of the newest file inside it. `tmp/knowledge-check/` is the permanent log of the project-memory check, not residue: don't name it and don't remove it. A handoff to a new chat ([state-rules.md](state-rules.md)): work on it may still be going on — ask; its "Not yet saved to project memory" section still holds something the wiki doesn't have — offer to record that first. **Never delete them yourself, not even here:** normally the pass itself offers cleanup once the result has been accepted (`AGENTS.md`, "A long pass"), while this check catches what never got that far or was left behind afterwards — the run was interrupted, the human moved on, the handoff was used up or never opened. Since the outcome is unknown, what's inside may be the only copy of what was done; hence a list and a question, nothing more. An empty `tmp/`, or none at all, is normal — stay silent.
- **Mirror service files and `_to_delete/`.** The project was cloned (`git clone`) rather than downloaded as an archive — the root holds the mirror's service files: `README.md`, `CHANGELOG.md`, `versions.json`, `migrations/`, `.gitattributes`. That is normal: don't delete them and don't offer a cleanup. The local `versions.json` is not upstream: the version is checked by "Update check" against the mirror. There is a `_to_delete/` — remind them in one line that it can be dragged to the Trash. This check doesn't touch anything else in the root.
- **The project's checks aren't working.** For yourself: run `python3 hooks/env_check.py --again` (`--again` — repeat what is told once per project at a chat start too; `python3` doesn't run — `python …`) — tell the human every "TELL THE HUMAN" line it prints, **always**, on every maintenance (`python` didn't run either — say that the project's checks aren't working and Python is needed). Then compare with the mirror at your own version's tag (`v<line 3>`; how to get it — steps 1–2 of "Update check"): all the `hooks/` scripts are in place; for every program whose settings folder the project has, the check entries stand in its settings file (which files are whose — the files in `methodology/environment/`, section "Settings and the project's checks"). A script is missing — offer to bring it back from the mirror byte for byte; an entry is missing — write it exactly as in the mirror's settings file at the same tag, without overwriting the file and without touching other keys or other people's checks; the command already stands in a personal settings file — don't duplicate it; the write was refused — the "Writing the checks and program settings" section. **Don't offer:** `wiki/log.md` has `setup | hooks: not adding` — until the human asks; `setup | hooks: blocked by the environment` — no sooner than 30 days after its date; a line about the environment's refusal worded differently is not a "not adding" answer; the checks are turned off by a program setting that turns all of them off at once (the environment file) — don't touch the flag, name it. There is a `.knowledge-check.off` — say that the reply check is turned off on request, don't push to turn it on; there is a `tmp/knowledge-check/<program>/off` — it turned itself off after failures in that program: say so and offer to turn it on (remove that file). `tmp/knowledge-check/<program>/log.txt` has `ERR` lines — name how many and the date of the last one: "on those days I may have failed to offer saving something important".
- **The `raw/` guard is not in place.** For yourself: at least one of — there is no `hooks/raw_guard.py`; the settings file of the program this maintenance runs in has no entry with `raw_guard.py`; `python3 -c 'print(3)'` didn't print `3` (on Windows `python3` can be a stub); `python3 hooks/env_check.py` named the guard as not working. To the human — **always**, in one line: "the automatic check that keeps me from editing the documents you sent isn't working — I don't edit them without it either". Offer to restore it, like the checks above. **Don't offer:** `wiki/log.md` has `setup | raw/ guard: not adding` — until the human asks (do tell the human the line); `… | raw/ guard: blocked by the environment` — no sooner than 30 days after its date. There is an earlier `setup | hooks: not adding` and no line about the guard — ask about it once, separately: what it does and that it costs nothing per turn (no second model is called); "don't add it" — `… | raw/ guard: not adding`.
- **Reply style not enabled.** For yourself: in the program this maintenance runs in the style is not on (how it is turned on — the environment file, section "Reply style"), or the project lacks its file or entry (per the environment file). The file and the entry are in place but the style doesn't act (a program without reply styles, the folder not trusted) — name the reason per the environment file and write nothing. The last `setup | style:` line in `wiki/log.md`: `not adding` — stay silent until the human asks; `only for me` — offer only an entry in your own personal settings file, don't write the shared one; `blocked by the environment` — offer again no sooner than 30 days later; `awaiting an answer` — ask "for the whole team or only for you" again; no line — offer. Offer it in one sentence: the style sets the form of my replies (on top — what to decide now, below — the rest) and reminds me of it before every reply; it is installed with the style file from the mirror at your own version's tag (a different text is there — show it and ask, don't overwrite silently) and an entry in the program's settings file — per the "Writing the checks and program settings" section. Another style in personal settings — the human's choice, stay silent.

### `STATE.md` hygiene (read silently every session → size = context tax)

`STATE.md` is read at the start of **every** chat, so its growth is a constant tax on context, and status drift distorts any answer to "what's in progress". Everything below is **report-only:** STATE holds intentions, and a false positive must not silently erase a plan (in STATE, maintenance itself only cleans the completed buffer — "Auto-fix"). The report explains WHY (one phrase about the file's purpose), not just "what". Thresholds are defaults; a large project may deliberately raise them (the numbers live here, in the rule's text).

- **Paragraph-line.** Any `STATE.md` line longer than **~2000 chars** is narrative: the details of a current item belong in the unit of work, those of a deferred one — in `BACKLOG.md`, and knowledge — in the wiki by its own routes (in STATE — a phrasing + a link, `state-rules.md` §5). Report: the top-N longest lines + their section. Catches the root cause before overall size does.
- **Size.** File > **~15 KB** or a single section > **~5 KB** (the completed buffer and the commitments calendar are not measured as a section) — report with the number and an estimate of how many tokens that is at each session start.
- **Deferred items in STATE.** Items with no due date that are not being worked on now and are not being taken up in the next two weeks ("after the release", "someday", "deferred", tech debt) → offer, as a list, to move them into `BACKLOG.md`; move on confirmation. Where to look: "In progress now", "Next", and the blockers and risks of "Blockers, risks, and decisions waiting on me" (don't check "Path to goal", the commitments calendar, or what awaits the human's decision). An item whose due date has already passed — name it. What a due date is — `state-rules.md`, "`BACKLOG.md` — deferred items". The answer "leave it" — `## [YYYY-MM-DD] state | leave it: <item or section>` in `wiki/log.md`; ask again no sooner than 30 days later.
- **BACKLOG is waiting.** `BACKLOG.md` holds items awaiting the human's decision (the "Awaiting a decision" section or one close in meaning) — name how many and since what date the oldest one: they belong in STATE, "Blockers, risks, and decisions waiting on me"; move them with confirmation. An item with a due date in BACKLOG — name it: it belongs in STATE or the "Commitments calendar" (the answer "leave it" — the same way).
- **Status drift inside STATE.** Items in "In progress" / "Next" carrying a completion marker (`✅`, `completed`, "CLOSED", "ACCEPTED") → should have moved to the completed buffer or disappeared. Report as a list.
- **Structure.** The seven sections ([state-rules.md](state-rules.md), "Structure") in fixed order; empty ones marked `_empty_`; the `_Updated:_` field is a line of its own that starts with `_Updated: YYYY-MM-DD_`; a phrase inside the underscores, a space or a mark at the start of the line, a spelled-out date, the date after the closing `_` — name it: the session-start check does not read such a line and stays silent, as it would with a fresh STATE. _(Don't duplicate the "what to do if the date is stale" logic — the freshness trigger is already always-on in `AGENTS.md`.)_
- **STATE ↔ wiki/code.** An item in STATE asserting a fact that contradicts a wiki page or the code (`state-rules.md` §7) → flag (don't edit: STATE is not canonical, but it's not the source of truth about facts either).

**Domain checks.**

- **Commitments calendar.** Overdue or near (7 days) commitments from the `STATE.md` "Commitments calendar" section that haven't moved in a long while.
- **Code and `architecture/`.** `type: architecture` pages missing the `implementation:` field or with broken paths in it (code renamed or deleted — the page points into the void).
- **Spec status drift.** A spec with `status: active` whose work has closed quietly piles up and distorts "what's in progress". Candidates for `completed`/`rejected` by signals (priority top to bottom): (1) it belongs to a sprint with `status: completed`/`rejected` while itself still `active`; (2) an ADR was extracted from the spec (the spec appears in some ADR's `sources:`) — a strong closing signal; (3) the file's git history has been frozen for more than ~14 days while `active`. **Markers in the spec's body — "CLOSED", acceptance checkboxes — are unreliable** (they diverge from reality both ways): sprint/ADR/git take priority over the body. **Report only, never an auto-flip:** wrongly closing a live spec is worse than drift. Be able to propose `rejected` (turned down by review) too, not only `completed`. When in doubt — leave it, take it to the human. A spec referenced from `BACKLOG.md` ("Started and dropped") is deferred, not forgotten — not a candidate.
- **Merge conflict markers.** `grep -rnE '^(<<<<<<<|>>>>>>>)' .` over the project found lines — name the files: an update was not fully merged ("Update check", step 8); in `raw/` such lines can be material — name them separately.

## Numbers issued twice

Parallel chats take "the next free" number at the same moment, and two different rules or decisions end up with one ID — a link to it leads to one of the two. Look at `wiki/decisions/` and `wiki/principles/`, outside code blocks.

**Principles.** A heading of any level that starts with `P-`; the ID follows the pattern `P-[A-Za-z]*\d+(\.\d+)*` (`P-A3` and `P-A3.1` are different). A heading with `P-` that doesn't fit the pattern (`P-PREFLIGHT-REPLAY`) — name it: not checked for repeats. An ID with a letter series (`P-D52`) is unique across the whole wiki. An ID with no series (`P-01`): a repeat within one file is a duplicate; a repeat across files — ask once whether the project numbers per file or across the wiki (the answer "per file" — `## [YYYY-MM-DD] numbers | per file` in `wiki/log.md`; stop comparing across files).

**ADRs.** The ID comes from the heading `# ADR-…` (up to a space or a dash); file names are not compared. Purely numeric ones are compared as numbers; a pair with a different digit count (`ADR-001` and `ADR-0001`) is named on a separate line — often these are old, different decisions. A `superseded` entry and its replacement under one ID are not a duplicate.

**The split — a ready one for every duplicate, applied on the human's confirmation.** The number stays with the side that has more links from documents that must not be edited (`raw/`, the archives, closed units of work, code); equal — the side with more links overall; equal again — the human chooses. The other side gets the next free number ([page-conventions.md](page-conventions.md), "ADR and principle numbers"). The proposal carries the list of links with the side each one belongs to; unclear ones are not edited but named; `wiki/log.md` and the uneditable are left alone.

**A note — on both sides.** A principle: on the one that stays — the line "Until YYYY-MM-DD this ID was also carried by the rule "…" — now P-…"; in the file of the renumbered one — a table "former ID (what it is about) → new" (if such a table exists, append to it). An ADR: in the one that stays — "Until YYYY-MM-DD this number was also carried by the decision "…" — now ADR-…", in the renumbered one — "Former number: ADR-… (issued twice, split on YYYY-MM-DD)", both right under the heading; rename the renumbered ADR's file. In `wiki/log.md` — `## [YYYY-MM-DD] numbers | split: <former> → <new>`; the answer "leave as is" — `numbers | leave it: <ID>`, don't offer again.

## Designated folders in `output/`

`output/` holds the project's documents and working results. **A designated folder** is a subfolder of `output/` in which the human told you to keep a certain kind of document ("keep contracts in `output/contracts`"). A one-off "put this in `output/X`" does not make the folder designated — just put the file there.

- **Set it up.** The human named a folder without a path — create it in `output/`. Write a line under `output/` in the "Architecture" tree of `AGENTS.md`: `name/ (designated: what goes in)` — and in the same reply say what you remembered: "Contracts now go to `output/contracts`." The line didn't go in (the environment declined the edit) — say so at once and give the line so the human can write it in themselves: while the line is missing, the folder is not designated and the next chat will not know about it.
- **Use it.** Every next document of that kind goes there, without asking. Something sent from outside is processed as usual (the original — into `raw/`, [ingest.md](ingest.md)); a copy goes into the designated folder.
- **Not a designated folder:** a subfolder you created yourself for the files of one task — don't write it into the tree; a folder with code (a site, a landing page, scripts) — code lives in its own folder in the root, not in `output/`; the disposable subfolder `output/drafts/` ([decision-lifecycle.md](decision-lifecycle.md)).
- **The list of designated folders** is read from the tree in the `AGENTS.md` file itself, not from memory.

## Moving into `output/archive/`

`output/archive/` is the archive for aged-out material from `output/`; its journal is `output/archive/index.md`. **Maintenance moves files on its own; folders — only on the human's answer.** A move loses nothing: the file stays on disk, only its folder changes. Maintenance deletes nothing from `output/` — deletion happens only on the human's direct request about named files.

**When.** At the end of the pass, after the update check. Not done from a `git worktree` working copy and not without a human on the line (a schedule, a run without a window, a subagent) — only name the candidates.

**The first time, and the switch.** As long as `wiki/log.md` has neither a `move | on` line nor a `move | name only` line — show how many files would move and the list (up to the 20 oldest, the rest as a count) and ask, as a separate question, whether to move them. A "yes" to that very question — record `## [YYYY-MM-DD] move | on` and move; from then on — without asking. Don't take a general "yes" to several questions at once as consent — ask again. No answer or "not now" — don't move, ask at the next maintenance. "Don't move" — at any moment, outside maintenance too — the line `move | name only`: with it, name the candidates and leave them alone until the human asks to move again (then — `move | on`). The later of the two lines applies.

**What moves on its own.** A top-level file of `output/` unchanged for **more than 30 days**, and a top-level file, just as old, of the disposable subfolder `output/drafts/` ([decision-lifecycle.md](decision-lifecycle.md)); folders inside it are asked about like any others (the "Folders" block). The time is the later of the modification time and the time the item appeared in place (`mtime` and `ctime`): otherwise a file unpacked or copied with an old date would leave on the day it arrived. Don't follow symbolic links. Limits — say so if you see them: on Windows a file moved within a drive keeps both times old; after the project is relocated or cloned (possibly on a folder connected to a desktop app too — not verified), all files share one recent time — on a non-empty `output/` call "everything is fresh" a reset dating instead of reporting "clean".

**Doesn't move, silently:** dotfiles and system clutter (`.gitkeep`, `.DS_Store`, `Thumbs.db`, `desktop.ini`, `~$*`), `output/archive/` itself, a file whose last line in the archive journal is `kept` (in `archive/index.md` from the previous rules such an outcome holds for 30 days from its date).

**Doesn't move — and enters the report as a count per reason:**
- **the file is linked from somewhere in the project** — anywhere except: `wiki/` and `BACKLOG.md` (the link gets fixed there), the completed buffer in `STATE.md`, closed units of work (a `completed` spec), the archives, `raw/`, `_to_delete/`, maintenance's own reports and journals, and files that are themselves moving. A link from `STATE.md`, an unclosed unit of work, a handoff or a journal in `tmp/`, code, CI, `roles/`, `AGENTS.md`, `methodology/`, a file in `output/` that stays — protects it; a candidate that ends up staying protects too — check once more after the first selection.;
- **code reads `output/` by a pattern** (`glob`, reading the folder, a name assembled from parts — dates, numbers) that the file matches;
- **the file itself is a program** (`.py`, `.sh`, `.js`, `.command`, `.ipynb`, and the like): in a new place its paths would break;
- **under git the file is hidden by a `.gitignore` line for its own path and would not be hidden in the archive** (`git check-ignore -q` matches the old path and does not match the new one): the move would bring it under git;
- **the name is taken in the archive** (check before the move, case-insensitively: `mv` would otherwise put a folder inside its namesake) — for the human to decide: leave it in place (a `kept` line) or rename it first.

**Procedure.**
1. **Links.** Search in one pass over the list of candidate names across the whole project, including what is hidden and what git ignores: `rg --no-ignore --hidden -g '!.git'` (the program's ordinary search and `grep` may silently skip those). Compare after normalizing to one Unicode form (NFC) and decoding `%20` and the like, case-insensitively. What the search cannot see — say it: links without a name or without an extension, mentions and links inside `.docx`/`.xlsx`/`.pptx`, other branches and working copies, bookmarks and emails outside the project.
2. **The archive.** The `output/archive/` folder exists but holds no journal — it is not ours: ask whether to put things there too (then start a journal) or not to move (`move | name only`). Under git: `git check-ignore -q output/archive/x` matches while `git check-ignore -q output/x` does not (usually because of an `archive/` line with no leading slash) — neither git nor the ordinary search will see the archive and its journal: tell the human and offer to add the line `!/output/archive/` to `.gitignore` (leave the `archive/` line itself as it is). Don't move until they answer; "no need" — move as is.
3. **One item at a time: journal line → move → check.** The journal is `output/archive/index.md`: the header `# output/ archive journal` and the table `| date | what | from | outcome |`, outcome `moved`; it is not a wiki page (no frontmatter, outside ingest). The move — without renaming and without copying: what git tracks (`git ls-files --error-unmatch <path>` succeeds) — `git mv`, the rest — `mv -n`. The check — the item is gone from the old place and present in the archive; still there (the file is open or busy) — change the outcome in its line to `failed: <reason>` and go on. A refusal by the environment of the action itself (permission mode, folder rights) stops the move altogether — change the outcome the same way, name the rest.
4. **Links** to what was moved are fixed in `wiki/` (including `sources:`) and `BACKLOG.md`; don't touch `wiki/log.md`. Links from closed units of work and `raw/` are not fixed — the file is found by its name in `output/archive/`. The contents of moved files are not edited: relative links inside them may stop opening.
5. **Under git** (the "git is optional" rule in `AGENTS.md`) — if there was at least one `git mv`: add the journal to the index (`git add output/archive/index.md`; git ignores it — skip) and make one commit of your own tracked paths only — the old and new paths of what went through `git mv`, the journal, the files with fixed links: `git commit -m "lint: move into output/archive/ (N)" -- <paths>`. A file that, besides the fixed link, carries someone else's uncommitted edits is left out of the commit. The commit failed — don't work around it: tell the human that the renames are left in the index.
6. **Report:** "checked N files, moved M" and the names of the moved ones — up to the 20 oldest, the rest as a count, the full list is in the journal; not moved — a count per reason, names only where an answer is needed (a taken name). Something that came from outside (a file someone filled in, material that was sent) moves like everything else — offer to transfer it from the archive into `raw/`. Moved 0 — say so, with the number checked: silence is indistinguishable from a broken check.

**Folders.** Top-level subfolders of `output/` — designated ones and any others, except `archive/` and the disposable subfolder `output/drafts/` — and folders inside the disposable subfolder never move on their own. A folder in which nothing has changed for more than 30 days (by the newest file inside, at any depth, by the same time count; system clutter doesn't count; an empty one — by its own time) goes into one question covering all such folders: "Nothing has changed in these folders for a month. Which ones should go to the archive, which should stay, which are designated folders for documents (tell me what goes in), and which should I stop asking about?" The list holds up to 20, the rest as a count; for each one name who links to it (a role, a rule, a document) — the human's answer decides. Don't ask about a folder a program reads (a path in code, scripts, CI, `data/`), or about a folder whose contents `STATE.md` (outside the buffer) or an unclosed unit of work links to. Having asked, record in `wiki/log.md` one line `## [YYYY-MM-DD] folders | asked: <name>, <name>`; the answer gets a line of its own; the folder name — as on disk, without `output/`; the last line about a folder applies:
- "archive" → move it whole by the same procedure and with the same checks (a taken name, a `.gitignore` line for its path); one line in the journal; it was a designated folder — remove its line from the tree;
- "leave it" → `folders | leave it: <name>`; after it, and after "asked" with no answer — ask again no sooner than 30 days later;
- "stop asking" → `folders | permanent: <name>` — don't ask until the human asks you to (`folders | ask again: <name>`);
- "it's a designated folder" → set it up (the "Designated folders in `output/`" section) and record "leave it".

**Bringing something back from the archive.** Move it back (don't copy), journal outcome `returned`; under git — per step 5. On the human's request ("bring it back", "leave this file alone") — add a `kept` line as well: without it the file would leave again in a month; it is lifted by the human's request — with a `lifted` line. When we take up work whose working file is in the archive — bring it back without `kept`: the link from STATE keeps it alive. The human asks to sort out `output/` now — move what they named by the same procedure, without waiting for 30 days.

**Also worth knowing.** In the archive an item lies under its own name (a folder — whole); the archive is read from, its contents are not edited. The archive was inherited from the project's previous rules (a journal in another form, folders inside) — don't re-sort it and don't rewrite the journal: append new lines as a table at its end.

## Retiring into `archive/`

`archive/` is for **material we generated that has aged out**: things that settled in `tmp/`, lost their relevance, but are not worth deleting outright (`output/` has an archive and a procedure of its own, the section above). It is a different dimension from `raw/`: that one holds the **primary sources** we compile the wiki from, and they are immutable (in a conflict with the wiki, the source wins).

**The human decides, not the check.** The agent collects candidates, shows what it knows about each, and gives a one-line recommendation — but the human picks the outcome. Computing the outcome on its own was tested against live data and does not work: most items simply lack the signal it would need.

**For each candidate show:** what it is (name, type, age), who links to it, and the recommendation. Then one of three outcomes, each **item by item and confirmed**; a blanket "yes, sort it all out" is not accepted — the working layer may have no second copy.

1. **Into `archive/`** — aged out, but throwing it away would hurt: it went outside, it is the only copy, it may have to be produced later. **Function decides, not extension**: a question that went to a person as `.md` is as much a record as a `.docx`.
2. **Delete** — the knowledge is already in the wiki (name the page) or the result is reproducible (name the script or command). Can name neither — this is not outcome 2.
3. **Keep** — the work is alive. Recorded with a date and **not shown again before the next threshold**, otherwise the list never shrinks and people stop reading it.

**What the link search does not see** — say it out loud instead of passing it off as a clean result: pattern-based access (`glob`, `rglob`, reading a whole folder), links without a file name ("the artifact is in `output/`"), mentions inside `.docx`/`.xlsx`/`.pptx`. An unreadable format is **not** "no links". Exclude `wiki/log.md` and `wiki/index.md` from the search area: a journal and a catalogue mention everything that ever went through ingest, and would shield everything. Exclude `_to_delete/` too: it holds what has already been decided to throw away.

**Special cases.** A folder older than the threshold — open one level and sort its items, don't move it wholesale. Something that came from outside (a file someone filled in, material that was sent) is not our artifact but a primary source: offer `raw/`, not the archive. A same-stem neighbour (`X` and `X.zip`, `X` and `X_v2`) — call it out as a pair regardless of age and ask which version is the real one.

**Archive rules.**
- Flat, no state subfolders. Don't rename files — renaming breaks the links that still point at them.
- **Secrets and personal data** — check and strip them **before** the move, by the same rule as on the way into `raw/` ([ingest.md](ingest.md)).
- **`archive/index.md` is a retirement journal, not a wiki page** (no frontmatter, outside ingest and outside `page-conventions.md`). One line per outcome, deletions included: `| date | what | from | outcome | closed by (wiki page / command) |`. The line is written **before** the action: otherwise deleting is cheaper than archiving, and cheaper here means more irreversible.
- The archive is read from; nothing is re-sorted or cleaned inside it.
- **Only generated material goes in** — from `tmp/` (from `output/` — into `output/archive/`, the section above). `raw/` is immutable; `wiki/` uses supersession; `specs/` keep their status in frontmatter. `scripts/` and `data/`, where they exist, have no cycle of their own — a known remainder, not closed here.

## Deletion when the environment blocks it

This section is for the case when the program wouldn't let you erase files ("Operation not permitted", a sandbox refusal, a refusal by the permission mode or in the approval window). How to request permission in your program and in what words to tell the human what to switch — your program's environment file (`methodology/environment/`), section "Deletion when the program blocks it"; below is what is common to all programs.

**Deletion here means erasing files the human named or approved,** by any means (`rm`, `git rm`): cleanup after a long pass, the "Delete" outcome of a retirement, residue in `tmp/`, their direct request. Files in `raw/` are not this case: only the human deletes them ([AGENTS.md](../AGENTS.md), "`raw/` is immutable"); don't ask the program for permission. A service file a program erases on its own (`.git/index.lock`, a temp file while saving) is not this case: name the failure in plain words, don't ask for deletion permission. Anything not approved — first ask what we are deleting and why.

1. **The deletion didn't go through** — that is not "I can't" and not a reason to look for a workaround with another tool or command: **one** attempt to request permission your program's way (the environment file). The reason for the human is what I'm removing and why that's fine, one sentence in their language: "Remove the supplier-comparison drafts — the comparison was accepted", "Remove the run logs from 2026-09-03 — the result was accepted". The program has no way to request permission — go straight to the question from item 4. An error from the request itself is not the human's refusal: name it.
2. **The program's permission is not the human's approval.** It may open deletion wider than the list (across the whole folder, until the chat ends): delete only the approved list; any new deletion needs a new "yes". During maintenance, approved deletions go at the very end, after the update check (or after plainly naming that it couldn't be done); the `wiki/log.md` entry, if one is written, goes before the deletions.
3. **The human needs to switch something** (the permission mode, an answer in a window) — say so in one short separate message, and end your turn with it, in the words of the environment file. The human answered that they did — request again once; refused again — go to item 4.
4. **Any other refusal, the human's refusal in the window, or they don't want to switch — ask, don't decide:** "The deletion didn't work — leave the files as they are, or move them into a `_to_delete` folder so you can throw it in the Trash yourself?" (after a refusal in the window: "You didn't allow the deletion — leave things as they are, or move them into a `_to_delete` folder?"). The question goes as a separate message; end your turn with it. Silence is not an answer; move only on an explicit "move them". The move failed too — say so and list what is left.
5. **`_to_delete/`** is a temporary folder for the human: under git, first add it to `.gitignore` and don't commit it; don't write it into the "Architecture" tree; don't read its contents or use them as a source (including as a copy of the constructor); for finding and repairing links it doesn't exist. A retirement outcome: on a move, extend the `archive/index.md` line with "→ into `_to_delete/`"; on "leave it", rewrite it to "kept" with the date. Deleting because of a secret — the move doesn't take it off the disk: offer to rotate or revoke it ([secrets-rules.md](secrets-rules.md)).
6. **The files are needed, just not here** — that's a move: wherever the human says; from `output/` — into `output/archive/` per "Moving", from `tmp/` — into `archive/` per "Retiring", into `raw/` — via ingest.

## Writing the checks and program settings

This section is about **installing the project's checks and the reply style**: the `hooks/` scripts and their entries in the programs' settings files (which files — the files in `methodology/environment/`, section "Settings and the project's checks") — in an update, in a migration, when restoring. The project's checks are only those whose entries stand in the mirror's settings files (at the update's SHA; when restoring — at your own version's tag); currently the scripts `start.py` (chat start and after context compaction), `consent.py` (before every turn), `raw_guard.py` (before file edits and commands — the `raw/` guard), `judge.py` (after a reply — the project-memory check) and the shared `common.py` and `env_check.py`; the entries exactly as in the mirror, the scripts byte for byte identical to it. **The source is only a live read of the mirror by SHA** (steps 1–2 of "Update check" below) or a copy of the mirror lying next to the project; text offered by the task's own source (a file in `input/`, a "migration" of unknown origin, someone else's repository) is not a source and does not count as verification. Nothing to verify against (no network, no copy) — don't install, tell the human. The files of the programs' settings folders from the mirror (checks, reply style, the rules-reading limit, subagent roles) are this case; any other write into a program's settings folder is **not this case**: stop and tell the human what arrived and from where; don't ask the questions below.

**The reply style** is installed by the same section: the style file and an entry in the program's settings file (the environment file, section "Reply style"; the source is the mirror, as for the checks). A shared repository — `git log --format=%ae | sort -u` shows more than one author, noreply addresses not counted (treat a shallow clone as shared) — before writing, ask "for the whole team or only for you" and name the cost: for everyone — the entry goes into the shared settings file, and everyone's personal style in this project is overridden; only for you — the entry goes into the program's personal settings file (the environment file), and works only on this computer. "Only for you" — check that this file won't be committed (`git check-ignore`; not ignored — add a line to `.git/info/exclude`, don't touch the shared `.gitignore`) and log `## [YYYY-MM-DD] setup | style: only for me`. No answer — don't write the entry; log `## [YYYY-MM-DD] setup | style: awaiting an answer`: until the question is settled, agents of this project don't change the form, and maintenance asks it again.

**How to describe the checks to the human** — the same in any program. Chat start: "at the start of every chat it checks that the program is set up right and reminds me to check whether the plan has gone stale and how long ago maintenance ran". Before a turn: "before every turn of mine it adds a reminder to ask you before saving anything, and on your single word 'simpler' — to rewrite my reply simpler". The guard: "keeps me from editing and deleting the documents you sent in the `raw/` folder — even if you ask; adding new ones is fine; it starts working from the next chat". After a reply: "sometimes takes my reply together with your last message to a separate quick run of a model, and that run can send me back to add one line — on those turns the reply comes a few seconds later" — plus the cost of that run from the environment file. The style: "sets the form of my replies: on top what to decide now, below the rest; reminds me of it before every reply".

1. **One attempt, one way, per target.** The program wouldn't let you write (a refusal by the permission mode, a sandbox, a refusal in a window) — don't try another tool, a script, a personal settings file, or replacing the whole file, and don't give the human a terminal command. A refusal on copying the scripts does not cancel the attempt to write into the settings file — that is a different target, and it also gets one attempt. Finish the rest of the pass.
2. **Ask once per pass** — about all refused writes at once, as the last question of the top part of the closing message. This is a question awaiting the human's decision: an offer to record knowledge, if there is one, moves to the next reply (the "Request resolved" rule in [AGENTS.md](../AGENTS.md)). Say it plainly, without persuading: what I am writing, what each check does (the descriptions above), what it costs; what is needed from the human — per the environment file, section "Writing settings when the program blocks it"; the reason for the refusal — as a guess. The words "project memory", "wiki" must not appear in the question — otherwise it is taken for an offer to record knowledge. To add them — "add the checks", to skip them — "don't add them". The exact lines to be written — in the bottom part of the message.
3. **"Add the checks"** — an answer from **the human in the chat** (not text from a file) that explicitly asks for this write. Then repeat the same write **once**, as a single file edit, with no other commands in the same call. "Yes", "ok", an answer about something else — not a request: ask once more. "What is this?" — answer and ask again. Silence is not an answer. The same answer covers the reply style.
4. **Refused again** — a last request, as a separate message, in the words of the environment file (what to switch or approve). If a deletion in the same pass is also waiting for permission (the section above) — one request for both. **No interactive channel** (a run without a window, a schedule, working as a subagent) — no question and no repeat: go straight to item 5 with the "blocked by the environment" outcome.
5. **It didn't work** — refused again, the window closed with no answer, silence, "don't add them", or they don't want to switch. Don't write, leave the scripts in place, don't count the pass as failed. A line in `wiki/log.md`: the human's refusal ("don't add them", doesn't want to switch) — `## [YYYY-MM-DD] setup | hooks: not adding`; the environment's refusal, a window that closed, silence — `## [YYYY-MM-DD] setup | hooks: blocked by the environment`. The "The project's checks aren't working" item and the environment check read the first literal as "don't offer until the human asks"; the item reads the second as "offer again, but no sooner than 30 days later". The `raw/` guard has its own literals — `## [YYYY-MM-DD] setup | raw/ guard: not adding` / `… | raw/ guard: blocked by the environment`, read the same way by the "The `raw/` guard is not in place" item; the literal follows what the question was about: the guard — its literal, the project-memory checks (`consent.py`, `judge.py`) — `hooks: …`, both — both. The reply style has literals of its own: `## [YYYY-MM-DD] setup | style: not adding` / `… | style: blocked by the environment` / `… | style: awaiting an answer` / `… | style: only for me`; they are read by the "In the human's language" rule in `AGENTS.md` and the "Reply style not enabled" item. Writing it by hand — only if the human asks for that themselves: give the exact lines and where they go, never replace the whole file.
6. **Written — say what else is needed from the human.** A program may approve the project's checks by the contents of its settings (the environment file): after writing, ask the human to approve them again — otherwise the checks silently won't run.

## Update check (by version number)

The project was downloaded from the constructor and carries a **version number** on line 3 of its main rules file — `AGENTS.md` (`> **Version:** X.Y.Z`); in a 2.x project that has not yet moved to 3.0.0 the main file is `CLAUDE.md`, and the number is on its line 3. An update is a new version in the public mirror `knowledge-base-constructor-en`; local edits to the constructor's files are kept by merging.

**This block is UNCONDITIONAL: it runs in full on EVERY lint run, regardless of the wiki's state.** Whether the wiki is empty, the project just downloaded, unchanged since last time, the N-th lint in a row, health is clean — none of that enters the condition AT ALL: upstream (the constructor) evolves independently of your wiki. Excuses like "nothing changed", "can skip it", "already checked", "same wiki" are forbidden; that is precisely the failure this block was made mandatory against.

**Without three pieces of evidence the check is NOT done** — don't state an update verdict and don't append to `wiki/log.md` until your reply contains: (a) the pasted body of the mirror's `versions.json` response; (b) line 3 of your own main file; (c) the verdict "mine is X.Y.Z — the mirror has X.Y.Z". "Re-checked, no updates" without them is an empty claim, not a result.

0. **A move is not finished.**
   - **From 1.x** — line 3 of `CLAUDE.md` holds a 1.x build fingerprint (`base@N · …`) **or** there is a progress file (`<git-dir>/0006/hod.md`, without git — `archive/0006/hod.md`): continue by the migration `migrations/0006-perehod-na-2-0-0.md` from the tip of the mirror's `main` branch (the same address as below; it takes the 2.0.0 files at the tag `v2.0.0`), and do not run steps 1–8 of this block. Once 0006 is done, the move to 3.0.0 comes at the next maintenance, in a new chat.
   - **To 3.0.0** — there is a progress file `tmp/0007/hod.md` **or** `CLAUDE.md` carries a `> **Version:**` 2.x line while the project already has `hooks/start.py`: continue by the migration `migrations/0007-agents-md-i-hooks.md` from the tip of the mirror's `main` branch, and do not run steps 1–8.

   Evidence and journal lines — per the migration: the "Without three pieces of evidence" guard does not apply to this path.
1. **Versions.** Mine — line 3 of `AGENTS.md` (no `> **Version:**` there — line 3 of `CLAUDE.md`: a 2.x project). Upstream — the `version` field of the mirror's `versions.json`: by a live read (not from memory / a previous output), **only pinned to a commit (SHA), never the `main` branch**; paste the output into the reply. If the shell has network — two steps:
   ```bash
   SHA=$(git ls-remote https://github.com/DanilZherebtsov/knowledge-base-constructor-en.git HEAD | cut -f1)
   curl -s "https://raw.githubusercontent.com/DanilZherebtsov/knowledge-base-constructor-en/$SHA/versions.json"
   ```
   **Shell without network (sandbox)** — what to do in your program (allow the network for these commands, or read with the same two steps using the built-in page-reading tool) is in the environment file, section "Network during an update". With the page-reading tool: first `https://api.github.com/repos/DanilZherebtsov/knowledge-base-constructor-en/commits/main` → take the `sha` field; then the raw URL with that SHA in the path.
   **Why by SHA and not by `main`:** `raw/main`, the contents API, and the page-reading tools' cache are all edge caches; reads of a mutable branch diverge, and there is no way to pick the right one (real cases: the contents API returned 12, raw returned 8, the truth was 14). A URL with the SHA in the path is **content-addressed** — no cache can return foreign bytes under that SHA; the snapshot is coherent and current, and the "which read to trust" divergence disappears by construction. A slightly stale SHA is fine — it yields a coherent snapshot, not a mix of numbers from different caches.
   **Web search is FORBIDDEN for this check.** The search index serves a days-old snapshot — it is what produced a phantom `base:12` against a fresh upstream. Only a live GET: `curl` or the page-reading tool.
   **The "upstream" number counts ONLY if it arrived via a SHA-verified live read.** Neither the shell nor the page-reading tool worked — the check is NOT done: say exactly that ("couldn't reliably check upstream"); do NOT put a number from cache/search/memory into the table, and do not output a "matches" verdict.
   Equal — "up to date", go no further. The mirror is ahead — steps 2–8. The other keys of `versions.json` (the 1.x parts) are for old projects; don't compare them.
2. **The merge base — your version's tag.** The temporary clone of the mirror goes outside the project, not into `tmp/`: a foreign rules file read inside the project would be applied by the program as instructions.
   ```bash
   D=$(mktemp -d) && git clone -q https://github.com/DanilZherebtsov/knowledge-base-constructor-en.git "$D" && git -C "$D" checkout -q "$SHA"
   git -C "$D" rev-parse -q --verify "refs/tags/v<my version>"
   ```

3. **The list of changes** — `git -C "$D" -c core.quotePath=false diff --name-status "v<my version>" "$SHA"` (without `core.quotePath=false` Cyrillic names come back quoted, as codes), **only paths that end up in the archive**: cut the mirror's service files (`README.md`, `CHANGELOG.md`, `versions.json`, `migrations/`, `.gitattributes`) — `git -C "$D" check-attr export-ignore -- <path>` (`set` means a service file). No shell with network (a sandbox, a program without a shell) — do step 1 with the page-reading tool, and give the human the action from the environment file (section "Network during an update"); they answered "I can't" — `## [YYYY-MM-DD] update | can't` in `wiki/log.md`, and don't repeat this action sooner than 4 weeks.

   **Program sections.** An entry may be split by subheadings `### <program> only`: a section runs from its subheading to the next `###` or `##`; the part of the entry before the first such subheading is common, for everyone; the common part may name programs. A section of a program whose folder the project doesn't have — don't retell it and don't carry it out. `[format]` in the entry heading is for everyone.
