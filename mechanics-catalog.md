# Constructor mechanics catalog

The registry of detachable mechanics. The constructor reads it to know which mechanics exist, what each one touches, and what it depends on. A preset manifest (`presets/<class>.md`) lists the chosen mechanics in its `mechanics:` field; the assembler ([ASSEMBLY.md](ASSEMBLY.md)) executes each one's `mechanics/<name>/_about.md`.

## Composition rules

- **The visual is the second competence axis, and it is ON for everyone.** `design` does not occupy the central type and composes with any lifecycle. It is wired into every preset by default: "will you be making things people look at" gets a yes almost every time and therefore discriminates nothing — so the interview does not ask it (the admission rule of ADR-0030). It is a separate part in `versions.json` rather than a chunk of base because its list of category defaults goes stale faster than anything else and must bump without dragging the base version along.
- **With `design` + `software-engineering` there is ONE cycle — the code one.** The visual does not open a second statement gate and adds no subagent rounds: it inserts the design read into the statement and a visual pass into the acceptance criteria. Ownership is split — code owns files and execution, the visual owns the decision and acceptance by eye. Without this rule a real landing-page task doubles the subagent count (the lesson of ADR-0034).

- **Central-type exclusivity.** `claim-graph` (type `claims/`), `spec-lifecycle` (type `architecture/`), and `decision-lifecycle` (type `entities/`) each claim their own central type. A project has one central type — these three are mutually exclusive as the "core". `software-engineering` doesn't occupy a central type (an overlay) — compatible with any class lifecycle.
- **Criterion for the central type — by how knowledge goes bad** (ADR-0030). The question: **does the project revisit its own conclusions, or does it act and move on?**
  - **Revisits → `claim-graph`.** A claim lives for a long time, its status shifts as new data arrives, and a refutation **cascades** through dependencies: the `supports/contradicts/refines` edges are a "rests on" link (as opposed to `supersedes` — "replaced by"), so a fallen claim must wake up everything that stood on it. Here: research, due diligence, investigation, competitive intelligence.
  - **Acts and moves on → the class lifecycle** (`spec-` / `decision-`). Knowledge goes bad not because we were wrong but because the world moved on; supersession handles it (mark the old, write the new), and the grounds are never re-examined. Here: saas, running a business.
  - The criterion binds to a **trait, not to a class name**: a new class that falls under "revisits" takes `claim-graph` without any edit to these rules.
  - **Not a reason to take `claim-graph`:** "I want knowledge to rest on sources." That's base already, and every class gets it — mandatory `sources:` (lint won't pass a page without them), citation localization, hypothesis statuses `open/validated/invalidated` in `discovery/`, supersession, and contradiction handling at ingest ("mark both sides, put it to the human"). `claim-graph` adds not the grounding but the cascade of refutation.
- **Clash resolution — on the assembler, silently.** Two contenders — the one the criterion above points at wins; the loser isn't wired in. The choice is **not** put to the human (they have no basis for it — they'll answer "I need everything"), and internal words are never shown. What goes out is only the consequence, in their language, and only if there is one for them at all.
- **Code is one competence mechanic.** All work on code (writing, ownership, deploys) lives in `software-engineering`: it is an overlay, doesn't occupy the central type, and **composes** with any lifecycle. In saas it pairs with `spec-lifecycle` (the spec = the unit of work, `software-engineering` = the execution). There is no exclusivity between the code mechanic and the class lifecycle — they are different axes (what we track vs how we write code).
- **Optional dependencies.** A dependency may be soft (a mechanic works without an optional co-mechanic). The assembler wires a dependency in only if it's listed in the preset's `mechanics` (or is mandatory, like `claim-graph` for `question-lifecycle`).
- **Deactivation.** An optional mechanic NOT in the preset's `mechanics` is simply not placed into the project. The base skeleton is **not** uprooted: base machinery (including **roles** — `roles.md`, `roles/_template.md`, the "Roles" section) is always present and cannot be switched off (ADR-0027; the former "deactivate roles" branch was removed together with that mechanic).
- **Lift, not fork.** A generic improvement discovered while extracting a mechanic from a class is lifted into base/the mechanic, not left as a copy in the class (legacy of ADR-0013).
