# CHANGELOG — constructor

The single version journal for all constructor parts. Part versions live in [versions.json](versions.json); each part (base, the mechanics) is versioned **independently**: an edit to a single mechanic bumps only its number — `base` does not grow with it. Assembled projects catch updates during maintenance via the build fingerprint (`base@N · <mechanics>@N`).

**One file, entries tagged by part.** Entry header — `## <part>@<version>` (e.g. `## base@19`, `## spec-lifecycle@2`). Grouped by part, newest version on top. Mechanics have no separate changelogs — everything lives here. (Preset manifests are not tracked here: their "changelog" is the `presets/<class>.md` file itself; maintenance reads it directly.)

**Discipline (for the constructor developer).** **Bumped a part's version in `versions.json` — write the `## <part>@<version>` entry here in the SAME commit.** Without it, a downstream project catches a bump during maintenance that it can neither classify nor explain to the human (real cases: base@18 and spec-lifecycle@2 shipped without entries — maintenance rightly refused to apply them blindly). The gatekeeper `publish-constructor.yml` → `.github/scripts/check_changelogs.py` blocks mirror publication if a part's number in `versions.json` and its top entry here have diverged.

**What goes into an entry (otherwise it's useless for triage on the other side):** the impact label — `[instruction]` (prose/rule, wiki knowledge untouched) or `[format]` (a new field/section on wiki pages → migration needed; add "how to adopt": what to migrate, lazy/eager/skip); and the **concrete substance** — which files/rules changed and why, in terms that let downstream classify the blast radius on its own and translate it for the human. Not "aligned with vN": a terse entry hides the edits.

## base@26
`[instruction]` **Citation localization is a base rule for every class (lifted out of research).** Previously the rule "**A citation carries a location**" lived in the `CITE-LOC` slot and reached only classes wired with `claim-graph` (research); for saas and business the slot resolved to empty, and their pages could point at a source without naming the place ("the 12.03 call" instead of "the 12.03 call, 14:20"). Being checkable six months later is a universal need, and the rule costs one line, so it is lifted into `page-conventions.md` unconditionally (lift, not fork — the legacy of ADR-0013). The `CITE-LOC` slot is retired; slot S7 in the `CLAUDE.md` skeleton is rewritten (the `claim-graph` mechanic now **hardens** the base rule into a lint check rather than introducing it). The saas/business/research manifests are corrected in their S7b comments — preset versions do not grow from this (a comment doesn't change what the class bakes into a project). **Downstream:** `methodology/page-conventions.md` is swapped during maintenance; a **retroactive lint check is deliberately NOT introduced** — pages written before the rule are not flagged (otherwise the first maintenance run would emit a report covering the project's entire history; discipline #5). The rule governs new pages. Wiki knowledge untouched. Knowledge — ADR-0030.

## base@25
`[instruction]` **Currency is a universal bootstrap-interview question; there is no default.** Previously the currency convention lived as a hardcoded default in preset manifests ("rubles with a space as thousands separator"), and an assembled project got rubles even when its money was in another currency; with the English edition of the constructor (ADR-0029) the cultural default became an error by construction. Now `bootstrap.md` (Step 1) always — for any class, outside the INTERVIEW-Q slot, like the code question — asks about the currency and amount format; the answer fills slot S8 "Documents and naming"; the question is skipped only if S8 is already filled. The S8 slot description in the `CLAUDE.md` skeleton is updated. The saas-product@3 and business-run-general@2 manifests no longer carry a currency default (research-project never hardcoded a currency). **Downstream:** existing projects are unaffected — their S8 is already filled with the chosen currency; nothing to do. Wiki knowledge untouched.

## base@24
`[instruction]` **Roles are universal base machinery, not a detachable mechanic.** Previously base carried the roles skeleton, and a preset without roles would *rip it out* (the "Deactivate" branch of the `roles` mechanic), and the interview question "do you need roles?" could trigger that deactivation even for a class where roles are the default (business). The result: the promise "a role can be created at any moment" lived in a deletable place — answering "no roles for now" removed `roles.md`/`roles/`/the "Roles" section together with the promise itself (bug class [ADR-0021]). Now the roles machinery (`methodology/roles.md`, `roles/_template.md`, the "## Roles" section, the bootstrap line) is a **non-detachable part of base**; the deactivation path is removed; the separate optional `roles` mechanic is **retired** (`roles@2`, the key removed from `versions.json`). The "## Roles" section and the bootstrap line gained an affordance: you can drop a role description and materials into `input/` in advance — then on "create role" the role is created well-informed right away. The interview ([START-HERE.md](START-HERE.md) Step 2) **no longer asks about roles** at assembly (premature); onboarding (Step 6) tells the human a role can be created at any moment. **Downstream:** any instance without roles in its fingerprint installs the machinery — migration `0002-roles-in-base.md`. Coordinated with `software-engineering@3`. Knowledge — ADR-0027 (revises the saas-OFF/research-refusal from ADR-0004). Wiki knowledge untouched.

## base@23
`[instruction]` The "think" phase (section "How Claude works on tasks") gained the **gate of confirming understanding before implementation**. Before a nontrivial task, Claude plays back to the human in checkable language: how it understood the task in its own words, what it changes and where, what result the human will see, where it interpreted something ambiguous / filled in an assumption — and waits for an explicit "yes". The same at **forks mid-work**: when human input is needed (a choice, a blocker, an ambiguity), the question is asked just as clearly (what the choice is, why it matters, the options + a recommendation); jargon removed or explained on the spot. The rationale is recorded: internal checks (including subagent gates) inherit the agent's reading of the task and do not catch divergence from the human's intent — only the human can catch it, so the confirmation comes before them. Closes the case: on a long task the agent understood the task its own way, conveyed the plan murkily and in jargon, the human rubber-stamped what they hadn't understood → the divergence surfaced after the failure. Coordinated with `software-engineering@2`. Knowledge — ADR-0026. Wiki knowledge untouched.

## base@22
`[instruction]` The "think" phase (section "How Claude works on tasks") hardened against sycophancy — blind agreement with the user's hypothesis. (1) Added to the phase's framing: "think" is not only "what is being asked" but also "is this the right thing to do"; evaluate the request, don't execute it on autopilot. (2) The former item "Object when justified" (reactive — it fired only on an obviously bad decision) is replaced by two: **"Separate intent from the proposed solution"** (extract the real goal, treat the user's proposed way as just one candidate, and when a better path exists — articulate it, argue for it, and bring it up for a joint decision) and **"No agreement by inertia, no objection for show"** (confirm directly when the user is right; object with an argument when the decision is bad; both extremes are miscalibration). The goal is calibrated honesty instead of reactive disagreement — and instead of the inverse pathology of "arguing to look independent". Knowledge — ADR-0025. Wiki knowledge untouched.

## base@21
`[instruction]` The code-ownership mechanic renamed `codebase` → `software-engineering` and expanded into the **full code competence** (it absorbed the execution cycle from `spec-lifecycle`). Three base touchpoints retargeted to the new name: the always-on catcher for "build code from scratch" in `CLAUDE.md` (section "Wiki: page types and operations"), the `OWNED-CODE` slot in `ingest.md`, and the code question in `bootstrap.md` (Step 1). The question-skip condition is now "the `software-engineering` mechanic is already wired" (previously — "a class with `spec-lifecycle` or `codebase`"), since code mechanics are no longer mutually exclusive (`codebase ⊥ spec-lifecycle` lifted). Coordinated update: apply together with `software-engineering@1` and `spec-lifecycle@4` — migrate a production instance per the instruction **`migrations/0001-software-engineering-split.md`**. Knowledge — ADR-0022. Wiki knowledge untouched.

## base@20
`[instruction]` In `CLAUDE.md` (section "Wiki: page types and operations") — an always-on catcher line for "build a site/bot/script/app from scratch": this is work on one's own code, not general consulting. If a code mechanic (`codebase`/`spec-lifecycle`) is wired — follow it; if not — do not default into advice about external no-code builders, but lay out the two readings (own code → offer to wire `codebase` + roles that "edit/deploy"; or no-code / delegating outside → we stay codeless) and record the choice. Closes a hole: the "build code from scratch" trigger lived only inside `codebase.md`, so a project assembled without that mechanic, on its very first "build me a site" request, silently drifted into general consulting and offered neither the mechanic nor the roles (real case: a project assembled as "there will be no code", first task — a website, the agent suggested a no-code builder without laying out the readings). The trigger is always-on → it catches at any stage, not only at assembly; the unreliable early interview answer to "will there be code" no longer does harm. Knowledge untouched.

## base@19

## base@18
`[instruction]` In `ingest.md` — an input-recognition gatekeeper: working source code (a code tree, a deployable site, scripts, a project with a build) is distinguished from ordinary material (a document/transcript/data/someone else's code sample). Your own code is NOT buried in `raw/` — it lives in a root folder matching what it is (`landing/`, `src/`, `scripts/`); only the knowledge about it goes into the wiki, not the code itself; the `OWNED-CODE` slot hooks up the optional `codebase` mechanic if it is wired in. In `bootstrap.md` — a universal interview question "will there be your own code?" (outside the INTERVIEW-Q slot) and the rule "the code folder is not created empty; it appears when code actually arrives". Closes a production-instance case: a finished landing page was not recognized as live code — ingest carried the site off into `raw/`, and the agent suggested keeping it in `output/`. Knowledge untouched.

## base@17
`[instruction]` The user-facing name of the lint operation is now "maintenance" ("run maintenance"): onboarding (ASSEMBLY step 9), the operations list and discipline §5 in `CLAUDE.md`, and the triggers and header of `lint.md` all lead with this word. ## base@16
`[instruction]` Flow B: completed the read channel that v15 left open. (1) When the shell has no network (sandbox) — read via the same two steps through `WebFetch` (a live GET that bypasses the local sandbox); do not fall back to web search. (2) **`WebSearch` is forbidden for this check** — the search index serves a snapshot that is days old; it is exactly what served up the phantom `base:12` against a fresh upstream (a relapse after v15). (3) The "upstream" number counts only when it comes from a SHA-verified live read; if neither the shell nor `WebFetch` worked — the check is NOT performed, no number from cache/search/memory goes into the table, and "matches" is not concluded. Knowledge untouched.

## base@15
`[instruction]` Flow B: read the version check **pinned to a commit, not to the `main` branch** — `git ls-remote` for the current HEAD, then the raw URL with that SHA in the path. Revokes v11's mistaken premise that the contents API is "fresh, uncached": both the contents API and `raw/main` are independent edge caches, either can lag, so two reads of the same branch yield diverging numbers with no way to pick the right one (real case: the API returned 12, raw returned 8, while the true value was 14). A URL with a SHA is content-addressed — the cache cannot return someone else's bytes; the "which read to trust" divergence disappears by construction. Knowledge untouched.

## base@14
`[instruction]` Flow B made UNCONDITIONAL: the version check runs on every lint regardless of the wiki's state (empty/fresh/unchanged/Nth run is no reason to skip) and does NOT finish without two shown artifacts — the pasted body of `versions.json` and the per-part comparison table with numbers; "no updates" is admissible only if the table shows `mine == upstream` for every part. Closes a relapse: on a freshly set-up empty wiki, lint reported "matches" three times without fetching the live `versions.json` (base@10/@11 hardened the text, but the "wiki is empty" context overrode it). ## spec-lifecycle@5
`[instruction]` A closing gate for exhaustive lists (cascade from `software-engineering@4`, "Blocker inside scope"). The "active → completed transition" section gained a condition: if the task statement enumerated an exhaustive list of elements, the move to `completed` is possible only when **every** element has an outcome — either done, or explicitly excluded by the human with the reason recorded in the spec; the `completed` status does not mask silent leftovers. Closes a production case: the task "integrate the ENTIRE regulatory base" was closed with the base only partially integrated; the uncovered categories settled as one-liners in STATE's "Next", untied to the original spec — discovered only a week later. Coordinated with `software-engineering@4`. Knowledge — ADR-0028. Wiki knowledge untouched.

## spec-lifecycle@4
`[instruction]` The mechanic is slimmed down to a **pure unit of work**. The code execution cycle (task statement → independent subagent review gate → implementation → repeat gate with test runs → report), the sprint plan gate, the runtime-`data/` rule, and the always-on injection of the cycle into the "act" phase are **moved out** into the new `software-engineering` mechanic (see `software-engineering@1` / base@21 / ADR-0022); spec-lifecycle keeps the spec/sprint/stages/ADR-on-close/synthesis and **refers** to `software-engineering` for execution. Plus **registry-defer** (ADR-0023): the "knowledge synthesis on closing" checklist no longer hardcodes "five types" — it says "walk through all the types declared in the project" (the "Architecture" tree in `CLAUDE.md`), so a project with horizontal extra types does not edit this managed file and does not lose the edit on update. **Coordinated update:** apply together with `software-engineering@1` — without it, the execution cycle is lost. Migrating a production instance (a mechanic split, not a file swap) — per the instruction **`migrations/0001-software-engineering-split.md`** (model — ADR-0024). Wiki knowledge untouched.

## spec-lifecycle@3
`[instruction]` Hardening of the execution cycle (production case: an overly broad gate condition → false metal codes → irreversible silent corruption of the calculator — the defect lived at the plan level; the value came from the gate BEFORE code). Four refinements: **(R1)** the sprint spec/plan passes an independent gate BEFORE the tasks start (decomposition, breadth of conditions and design assumptions, cumulative impact) — previously only task specs were gated, and plan-level defects slipped through; **(R2)** the post-code gate verifies correctness **by execution** — run/write tests, reproduce the behavior, not only agent code review; **(R3)** the gate scales with risk — the impact reviewer flags irreversibility / blast radius; irreversible or wide changes get more verifiers plus a separate adversarial round, routine ones — the baseline 3+1; **(R4)** a note for the human in the mechanic's text: naming the task is enough, the cycle is mandatory by default. Knowledge — ADR-0016 (the "Refinements" section). Wiki knowledge untouched.

## spec-lifecycle@2
`[instruction]` Between the spec and `completed` — a mandatory **execution cycle**: the spec before the code → a gate of 4 independent subagents (3 on correctness + 1 on impact on adjacent modules) → implementation → repeat gate → report; loop on errors; a gap inside scope goes back into the spec, a blocker outside scope goes to the human with options. The always-on pointer is inserted by the mechanic's wiring into "Principles → the 'act' phase" (not by editing base — base is shared with the codeless classes). Knowledge recorded in ADR-0016. Wiki knowledge untouched.

## software-engineering@4
`[instruction]` Against silent scope narrowing on "exhaustive" tasks ("the entire regulatory base", "all the integrations"). Three edits to the cycle: **(1)** step 1 (task statement) — a request that is exhaustive by nature must enumerate the full list of elements explicitly, not with a summarizing phrase (otherwise an exclusion is invisible both to the gate and to the human); **(2)** a new third case, **"Blocker inside scope"** (alongside "Gap inside scope" / "Blocker outside scope") — an element of the list that cannot be closed right now (typically: no test data to verify it against) does not slip silently into the backlog: first try to remove the cause yourself (construct representative data); if that fails — an explicit item in the report + the human's decision; the spec does not move to `completed` until every element has an outcome; **(3)** step 5 (report) — an outcome for every element of the list, not collapsed into a single backlog line. The reason: the agent decided on its own not to support the unverifiable part of the functionality and quietly shelved it as a "minor item" in STATE — silent corruption of the same rank (lost scope this time) as silent data corruption; both are symptoms of the same disease, "deciding without the human". Coordinated with `spec-lifecycle@5`. Knowledge — ADR-0028.

## software-engineering@2
`[instruction]` Step 1 of the cycle ("Task statement — before code") gained an explicit **human confirmation before the subagent gate**: first play the statement back to the human in plain words (how the task was understood, what changes and where, what the result will be, where assumptions were filled in) and get a "yes" — only then the statement gate (step 2). ## software-engineering@1
