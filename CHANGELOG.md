# CHANGELOG — constructor

The single version journal for all constructor parts. Part versions live in [versions.json](versions.json); each part (base, the mechanics) is versioned **independently**: an edit to a single mechanic bumps only its number — `base` does not grow with it. Assembled projects catch updates during maintenance via the build fingerprint (`base@N · <mechanics>@N`).

**One file, entries tagged by part.** Entry header — `## <part>@<version>` (e.g. `## base@19`, `## spec-lifecycle@2`). Grouped by part, newest version on top. Mechanics have no separate changelogs — everything lives here. (Preset manifests are not tracked here: their "changelog" is the `presets/<class>.md` file itself; maintenance reads it directly.)

**Discipline (for the constructor developer).** **Bumped a part's version in `versions.json` — write the `## <part>@<version>` entry here in the SAME commit.** Without it, a downstream project catches a bump during maintenance that it can neither classify nor explain to the human (real cases: base@18 and spec-lifecycle@2 shipped without entries — maintenance rightly refused to apply them blindly). The gatekeeper `publish-constructor.yml` → `.github/scripts/check_changelogs.py` blocks mirror publication if a part's number in `versions.json` and its top entry here have diverged.

**What goes into an entry (otherwise it's useless for triage on the other side):** the impact label — `[instruction]` (prose/rule, wiki knowledge untouched) or `[format]` (a new field/section on wiki pages → migration needed; add "how to adopt": what to migrate, lazy/eager/skip); and the **concrete substance** — which files/rules changed and why, in terms that let downstream classify the blast radius on its own and translate it for the human. Not "aligned with vN": a terse entry hides the edits.

## software-engineering@10
`[instruction]` **Extracting data from a foreign format: a boundary sample, a rejects journal, reconciliation of the total.** The mechanic said **how** code is written and checked, and (since `@6`) **how it survives an interruption**, but nothing about how to make sure the data it lifted matches the source. A real case: a parser for multi-page PDF tables did not account for a record that starts at the bottom of a sheet and continues on the next one; there was no exception, the output was plausible rows, and the corruption only surfaced after a large body of work had been built on top of it. The same class of failure as the empty impact lens (`@8`) and reviewers that cannot be launched (`@9`): **a failure indistinguishable from normal** — except that here what stays silent is a tool, not a procedure.

**New section "Extracting data from a foreign format — a boundary sample, reconciliation against the source"** (after "Long-running operations"). *When it kicks in* — the code lifts structured data out of a source that **is not** structured data: a PDF, a scan/OCR, an HTML page, a laid-out document, another system's export, an API that hands back pages; reading your own JSON, your own database, or a file with a published schema does not fall under it. *The boundaries are checked first, and before the bulk run* — the sample is assembled from the seams (a page break, the seam between batches/chunks, the end of a section, a change of template, the pagination edge, the first and last record): the middle parses correctly almost always, which is why a quick look at the beginning is reassuring and proves nothing; the typical case is named verbatim — a multi-page table and a record across a sheet break. *A silent parser is not a result*: the extraction must reject out loud (field count does not match, a required field is empty, a value will not convert, a fragment did not parse) into a **rejects journal** with the place in the source; a quiet `None`, empty string, or skipped record is a defect, not tidiness. *The total is reconciled against the source, not against itself* — an independent recount (number of records, sum of a control column, number of pages, last item); a discrepancy is a blocker, not a footnote. *Extraction is a separately accepted stage*: nothing is built on top of an unreconciled one, and what was lifted as-is (with coordinates in the source) is kept apart from whatever is derived from it — a fixed parser can then be replayed on its own instead of dragging the whole body of work along. *It adds up with a long-running operation* when the run is long.

**Step 1 of the cycle — a hook in the statement of work** (twin of the long-running-operations hook): the task lifts data out of a foreign format → the statement must name **what the correctness of the extraction is checked by** (which boundaries we sample, what we reconcile against the source), and the acceptance criteria must include that reconciliation; otherwise the statement is not accepted, because "the parser ran without errors" is not a check. **No separate lens is added** to the gate for this — the requirement lives in the statement and is checked by the existing lenses (the ADR-0034 calibration).

**Downstream:** additive, no migration needed — no new folders or fields, wiki knowledge untouched. **Adopt together with `base@36` or after it:** the core of the rule lives in base, this is the hardening and the code specifics. **How to adopt:** the file `methodology/software-engineering.md` is copied verbatim; the always-on line in the project's root `CLAUDE.md` needs no edit. The knowledge — ADR-0044.

## software-engineering@9
`[instruction]` **The reviewers cannot be launched — the step is not skipped in silence; recon degrades differently from the gate.** The mechanic defined independent review through the tool ("separate subagents (Agent/Task)") and stopped there. When subagents cannot be launched — absent in the environment, forbidden by session policy, the call refused — that definition read as "a gate is impossible", so step 2 ran inside the shared context, silently, and the report looked like a passed gate. The same class of failure ADR-0040 closed for the empty impact lens, one floor up: what was switched off was not the review's input but its mechanism.

**Step 2 (`software-engineering.md:33`)** — added to the definition: launching the reviewers did not work out → the step is not skipped and not passed in silence, the procedure is in [review-gate.md](review-gate.md), "The reviewers cannot be launched". **Step 4** is named separately, with a caveat: correctness there rests on the test run and is not lost — what is lost is the impact lens, and that is exactly how the report puts it, rather than "the re-review passed".

**The recon pass (`software-engineering.md:26`)** — a different trade-off, now stated explicitly: recon needs breadth of context rather than an independent view, so its honest degradation is a sequential sweep (each subsystem's result still lands on disk immediately). But recon **counts only by what has landed in the wiki as pages**; reading done in passing during the gate is not recon, however much of it there was, and it does not clear the empty-lens blocker. Without that caveat the degradation rule would have opened a bypass around ADR-0040: the "there was nothing to read" blocker could be cleared by shallow reading inside the gate.

**Downstream:** additive, no migration needed — no new folders or fields, wiki knowledge untouched. **Accept only together with `base@35` or after it:** the floor itself lives in `review-gate.md` (part of base); what is here is the references to it plus the code specifics. A project that takes the mechanic alone on `base@≤34` gets a reference to a section that does not exist. **How to accept:** `methodology/software-engineering.md` is copied verbatim; the always-on line in the project's root `CLAUDE.md` ("Code — only through the execution cycle…") needs **no** edit — the shape of the cycle did not change. Knowledge — ADR-0041.

## software-engineering@8
`[instruction]` **Code that arrives ready-made is described before the first task; an empty impact lens is a blocker on the statement.** The mechanic claimed work "from scratch **or on top of existing code**", but both doors (the gatekeeper in `ingest.md` and the decision to build from scratch) led into the same branch — "create the folder + offer the roles" — with no study of the code in it. Meanwhile step 2 of the cycle **leans on** knowledge of the system: the impact lens reads `wiki/` (for saas — `architecture/`). On an inherited base the wiki is empty, and the lens returns not "no impact" but nothing at all — silently, looking like a passed gate. That is, the main safeguard against irreversible change switched itself off in exactly the project where the risk is highest: the code is someone else's and nobody knows its invariants.

**A new section, "Code arrives ready-made — a reconnaissance pass first"** (before the execution cycle): *when* — the code folder was created by code arriving and there is no knowledge of the system, or it is known to have fallen behind (once per base; again for a large unfamiliar chunk); *how* — parallel subagents per subsystem, each with its own folder and context, tasked not with "assess the quality" but with **describing the observable** (what the module is, what it exposes, what it rests on, how it breaks), reading the code on disk rather than the `README` (which goes stale first), with reconnaissance over a large base treated as a long-running operation whose per-subsystem result lands on disk immediately; *where it lands* — as pages of the class's central type through ordinary ingest, with `implementation:` pointing at real paths, **a page per module or contract**, not one sheet titled "codebase overview"; *what gets flagged* — reconnaissance recovers **what is there**, not **what was meant**: intent and trade-offs are not readable from code, guesses about reasons are marked as guesses, and a recovered genuine choice becomes a separate ADR marked "reconstructed after the fact"; *what not to do* — no fixing and no refactoring along the way, the pass **reads**.

**Step 2 of the cycle — an explicit blocker:** no knowledge of the affected modules in the wiki → the lens reports "there was nothing to read", the task stops, and reconnaissance over the affected subsystems comes first (not necessarily the whole base). An empty lens counted as "no impact" is named the worst outcome a gate can have — it looks passed. Plus a fork in the code-folder section: code arrives → reconnaissance; from scratch → knowledge grows alongside the code through ordinary ingest, no reconnaissance needed.

**Downstream:** additive, no migration needed — no new folders or fields, wiki knowledge untouched. A project already maintaining inherited code with no description in the wiki will pick up the rule at prophylaxis and can close the reconnaissance in one pass. Knowledge — ADR-0040.

## base@36
`[instruction]` **Extraction from a document is a hypothesis, not a reading.** The constructor carried no rule at all about the correctness of data extraction (verified by `grep` over `base/`, `mechanics/`, `presets/`) — even though `HELP.md`, in its model "strong" task statement, offers the human exactly this scenario: "the folder holds PDF contracts — make a table: counterparty, tax ID, amount". A real case (a parser for multi-page PDF tables, a record across a sheet break, silent corruption discovered after a large body of work had been built on it) showed the hole is a general one: Claude lifts data out of foreign formats by hand too — a batch of contracts into a register, a table from a paper into a claim — and a page break breaks those just the same.

**(1)** `CLAUDE.md`, "the act phase", a new paragraph next to "A long pass": data lifted from a foreign format (a PDF, a scan, a page's layout, an export) is obtained by parsing a **rendering**, not a record — the structure is reconstructed by guesswork, and the guess **stays silent when it is wrong**, handing back plausible rows instead of an error. It goes wrong **at the boundaries** (a row across a page break, the seam between batches, the end of a section, the pagination edge). Hence the order: before the bulk run — a sample taken **precisely at the boundaries** (not at the first rows: the middle always parses correctly), afterwards — **reconciliation of the whole against the source** using something counted independently (number of records, sum of a column, last item); anything that does not add up or is unclear goes into the rejects list and to the human, not into the result as an empty value; until an extraction has been reconciled, nothing is built on top of it — whatever is built will have to be redone as well.

**(2)** `HELP.md`, "Techniques that work" — the same thing to the human in their own language: when I lift a table out of a document I parse its **appearance**, not a record; the typical corruption lives at the page breaks; I check the seams myself and show what did not add up; on data that matters, ask me to recount the total. The showcase is edited because the model task statement in that very file leads straight into this scenario.

**Downstream:** additive, no migration needed — no new folders or fields, wiki knowledge untouched. **How to adopt:** `HELP.md` is copied verbatim; in the project's root `CLAUDE.md` the paragraph is inserted after "A long pass" (the file is filled with instance slots and cannot be swapped wholesale) — the precedent for such an additive `CLAUDE.md` update is `base@30`. The code specifics (rejects journal, the trigger, the hook in the statement of work) live in `software-engineering@10`; a class without code gets only the base rule. The knowledge — ADR-0044.

## base@35
`[instruction]` **"The reviewers cannot be launched" is not "the gate passed".** Everywhere, the gate was written on the assumption that separate reviewers can always be raised. When they cannot — the tool is absent in this environment, launching them is forbidden by session policy, the call is refused — the behavior was not defined at all, and the practice turned out to be the worst available: the review ran inside the shared context, silently, and the report looked like a passed gate. The same failure `base@34` closed for the empty impact lens ("there was nothing to read" instead of "no impact"), except that this one switched off not the review's input but its mechanism — and stayed invisible all the more reliably.

**(1)** `methodology/review-gate.md`, new section **"The reviewers cannot be launched"**: the gate is neither cancelled nor passed in silence — it is passed weaker, and that is said out loud. **The refusal must be observable** (try first; "assumed it wasn't allowed" is not grounds — one shared context is cheaper and therefore pulls); the refusal applies to the task at hand and is not inherited onward through the session; a reviewer that launched and then failed is a failed lens, not an absent mechanism. **Irreversible and wide-impact work does not degrade at all:** a disproof round inside the shared context is not weakened but imitated — it disproves its own work and knows every earlier verdict; so: stop and ask the human. Below the strengthened contour: first everything that converts into settling it by doing is converted (its share grows rather than staying put); the remainder — passes with **different instructions**, not the same number of lenses (copies of one instruction inside a shared context create no independence); the outcome — **material for the human, not a verdict of "clean"**, disclosing exactly what changed: the checks ran in one shared context and did not check each other. The line about the mode is needed **only** in this branch: a normal pass says nothing about its own mode, otherwise the marker turns into a ritual and stops being read (the same principle as the silent startup checks). Plus the caveat on recon: what it needs is breadth of context, not independence — degradation by sequential sweep, but it counts only by what has landed in the wiki as pages.

**(2)** `methodology/review-gate.md`, section "Reviewers write nothing" — extended to the pass inside the shared context: while the check is running, `wiki/`, the statement and the working files are not touched. This is about write access, **not about scratch**: the pass's journal goes to `tmp/`, as with any long pass. Otherwise a context compaction mid-pass leaves an empty disk and the line "a gate was running" in the summary — and the cheapest move becomes counting the gate as having happened.

**(3)** `CLAUDE.md`, the always-on gate paragraph — three sentences verbatim (not a link): the refusal is observed; irreversible work does not degrade, stop and ask; below that — doing it first, then different instructions, and the report states plainly that it ran in one shared context. The rule fires at the moment when opening a `methodology/` file is already too late, so the floor has to sit in the always-on layer.

**(4)** `HELP.md`, the review bullet — the same thing said to the human in their language: sometimes the environment won't let the checks be spread apart, then the review happens in one head, there is nowhere for disagreements to come from, and it is weaker; this is said plainly rather than passed off as the full thing. Also softens the promise "I'll show where the checks disagreed" (in that mode there are no disagreements by construction) and states that the "check this thoroughly" lever cannot be delivered in it.

**Downstream:** additive, no migration needed — no new folders or fields, wiki knowledge untouched. **How to accept:** `methodology/review-gate.md` and `HELP.md` are copied verbatim; in the project's root `CLAUDE.md` the "independent review gate" paragraph is edited surgically — the three sentences from item (3) are inserted after "…lenses do not replace a run.", nothing else changes. Assembly fills in nothing: the edit introduces no slots. Knowledge — ADR-0041.

## base@34
`[instruction]` **An empty impact lens reports "empty", not "clean" — for all classes.** The same defect closed in the code mechanic lives in base: `review-gate.md` gives the impact lens the input "the knowledge in `wiki/`" and says nothing about the case where the wiki is empty on the area affected. A class without code hits this identically — a decision about a contract or a research conclusion passes a gate where the reviewer had nothing to read, and the report looks clean. **(1)** `methodology/review-gate.md`, "What the reviewers are tasked with" → "Impact on neighbouring areas": if the wiki is empty on the area affected, report exactly that ("there was nothing to read"), not "no impact"; an empty lens counted as a clean one is the worst outcome a gate can have, it looks passed; what follows is the human's call — build that knowledge first, or proceed with the risk explicitly accepted. **(2)** `methodology/ingest.md`, the gatekeeper, "working code" branch: the code arrived ready-made → before the first task on it, offer a reconnaissance pass (describe the modules and contracts into the wiki, a page per module), otherwise the task-statement review will read emptiness. ## design@2
`[instruction]` **The canvas as a routed surface + four blocks taken from the built-in `/design` skill.** A week after `design@1` Anthropic shipped a built-in skill — an artboard canvas published as an artifact. Analysis showed it is **not a rival to the mechanic but a surface underneath it**: it has no method for deriving directions, no ban on building your own top pick, no guessability test, no verification tags, and no accumulated memory of a brand identity (design-system import does not work in the Claude Code build — every task starts from scratch, which is exactly the hole `BRAND.md` fills). What it does have is what markdown fundamentally cannot give: the human sees the mockups side by side, edits them by hand and saves a version.

**(1) The block "The canvas — when the environment offers one"** in §5. Division of labour: the canvas shows, edits and accepts — **the file is delivered by the agent, from disk**, and that is not a preference but the only route outward: **the canvas cannot be shared publicly at all** (the download declaration is baked into the editor template; publishing without it does not open the link, it only breaks export — verified by trying). Directions are shown **once** (what to show is the mechanic's, how to show it is the canvas's). The human saved → read it back and continue from their version: republishing from stale files overwrites their edit silently; reading back is expensive — on purpose, never just in case. A deck belongs on the canvas first of all: N same-sized slides side by side *is* the contact sheet with its four acceptance lenses. Degradations are named, not silently worked around (export may not work; printing from the browser yields a screenshot of the interface, not the mockups). **The canvas is never made a dependency** — an early preview on paid plans, the same regime as the official pptx skill: route to it when present, never require it.

**(2) The rule above that whole block: never restate documentation as fact.** What you have not seen yourself, mark as unverified. It came from a miss during the shakedown: the canvas's PDF export was asserted from the skill's documentation, and the owner went looking for a button that does not exist. That breaks an already-recorded rule — "reporting a defect that does not exist is worse than missing one that does" — now extended from acceptance to any claim about the environment.

**(3) A new surface, "Print"** in §7 — posters, fliers, brochures; the section did not exist at all. The numbers are external, not our extrapolation: author at 96 px per inch (A4 794×1123, Letter 816×1056, A5 559×794, Tabloid 1056×1632), body no smaller than 12pt (16px), headlines with ~10% slack for the substitute face. Flier: one dominant element, a headline of six words at most at 60pt+, the five Ws in a tight group, flat blocks instead of photos and gradients, **a grayscale check**. Trifold: the panel order IS the fold order, and on the outside face the front cover is the **rightmost** panel. Plus print discipline (physical units, no vanishing hairlines, no huge dark flood fills).

**(4) Three rules into the quality bar:** hit targets no smaller than 44px in screen mockups; **no fake chrome** (a fake phone status bar and virtual keyboard — the system draws its own on top and the layout looks doubled); **the layout must survive direct manipulation** — groups of like things on `flex`/`grid` with `gap` rather than per-element margins, because `gap` survives dragging and deleting while whitespace text nodes do not. The last one is a new dimension: a rule not about how it looks but about what happens when a human moves a block by hand.

**(5) Someone else's brand identity is the single exception to "the brief wins"** (§2). A request to "make it like <company>" is neither executed literally nor declined, but broken down by list: the principle, the arrangement, rhythm, typography as a system, colour strategy, motion and tone are freely taken; the logo, a licensed typeface, recognisable brand elements and element-by-element reproduction are not. **"An exact copy" remains a legitimate item on that list when it is your own** — or when you have the source and the right: then the rule inverts into a requirement to copy exactly, from the source, without rounding values to a 4/8px grid. Which part is not being copied is named out loud.

**Downstream:** one file swap, `methodology/design.md`, during maintenance; no migration needed, wiki knowledge untouched, `base` unchanged. Knowledge — ADR-0043 (observations are dated: the preview changes, re-check at the next bump).

## design@1
`[instruction]` **New mechanic: the visual competence — landing pages, sets of graphics, presentations.** It closes a class of tasks that comes up for almost every user ("almost everyone makes a presentation at some point") and about which the constructor knew nothing: asked to "make a presentation", Claude either drifted into advice about external services or drew from habit — that is, shipped the category default. Distilled from three external sources (impeccable, Apache-2.0; taste-skill, MIT; emilkowalski/skills, MIT) and **shaken down over three real runs** on a live landing page: a critical review, five built first viewports, and a 13-slide sales deck in `.pptx`. Eleven rules in the file exist because those runs went wrong, not because someone reasoned them up.

**A single drop-in**, `methodology/design.md` — a five-step order: **(1) the design read** in one line (what · for whom · the job from a closed list · tone), written as a comment inside the source itself so it survives a dropped chat and a context compaction; "zero" is a legitimate outcome. **(2) What is already true** — four entry states judged from evidence rather than from whether a file exists (no authority / a settled world / an incomplete brand / a redesign), the "brief wins" rule and its flip side "a pinned world pins the world, not its softest rendition", and a catcher for incoming brand identity. **(3) Direction** — the core: name the category rut and throw it out, derive seven candidates **from the audience's world** (not from a catalogue of interface devices) with a minimum of three material families, show three (or as many as the human named — their word beats the rule) and **build not your own first**, the guessability test "if the aesthetic can be guessed from the category alone, rework it", colour strategy before colours, stop before code. **(4) The quality bar** — "verify" and "refuse", where **every rule carries a `[measured]` or `[eye]` tag**: a rule written into the floor and landing in neither a check nor an explicit "a human looks at this" list does not work — a direct lesson from the runs (the 65–75 character line measure sat in the file and was violated three times because nothing counted it). Plus a dated list of concrete faces, palettes and devices. **(5) Acceptance** — two bounded batches, not a loop: render → name what already works → one batch of fixes → one confirming pass → a fresh lens that does not inherit the build conversation → a one-word verdict from a closed list.

**Three things absent from the external sources that the shakedown produced:** "a screenshot shows you what to look at; it proves nothing" — overflow and clipping are **measured**, not eyeballed (a false positive nearly produced a report of a defect that did not exist); "when the environment cannot render, the human becomes the renderer" — a normal step, and what they find is turned into a check and run across the whole job, because one human finding almost always exposes a class; deck type sizes **split by medium** (projection ≥ 18–20pt versus a file at 12.5–16pt) — demanding projection sizes from a deck read on a laptop squeezes the text out of the frame.

**Exactly one artifact — `BRAND.md`** at the project root, and it is **never created on its own**: once the human has accepted the first visual piece of work, Claude offers, once, to save the approved style for the future — a one-off good-looking presentation does not have to become the project's brand identity. Declining is a normal outcome; on a second visual artifact the offer may be repeated with a concrete argument. Written **from what was built**, never in advance. A third axis of memory beside `wiki/` (what we know) and `STATE.md` (what we are doing): what the things we make look like. Deliberately not a wiki page — the wiki is maintained by Claude through ingest and demands `sources:`, whereas `BRAND.md` is edited by the human and is itself the source.

**Composition.** Takes neither the central type nor `DOMAIN-LINT`; works with any lifecycle. With `software-engineering` there is **ONE cycle, the code one**: the visual opens no second statement gate and adds no subagent rounds — it inserts the design read into the statement and a visual pass into the acceptance criteria (without this rule a real landing-page task doubles the subagent count — the lesson of ADR-0034). Without the code mechanic it works standalone, and that is the primary mode: presentations and graphics are made first and foremost by classes without code.

**A debt taken on knowingly:** the "Examples as of" section is dated and must be revisited at every bump of `design` — concrete faces and palettes are the tells of their year, while the normative part lives in the guessability test. Knowledge — ADR-0038.

## base@32
`[instruction]` **The independent review gate lifted out of the code mechanic into base — for every class.** Previously "the task statement is reviewed by independent subagents before execution" lived only in `software-engineering` and therefore reached only classes with code, although the class of problem is wider than code: a decision about a contract, a research conclusion, a letter to a counterparty also cost money, go outside, and land in the wiki as canonical. The new `methodology/review-gate.md` is the shared mechanism: what the gate catches (a missed requirement, an unrealistic acceptance criterion, a neighbouring area disturbed, an unnoticed irreversibility) and **what it does not** (divergence from the human's intent — reviewers inherit your reading, which is why "confirm understanding" comes before the gate, not instead of it); depth calibrated by risk (cosmetic — 2 lenses, routine — 3+1, irreversible or wide — plus a round on disproof) with a list of what counts as irreversible and a requirement for a **concrete flag** from the reviewer instead of a general sense that "the task is important"; the rule "if you can settle it by doing it, settle it by doing it" (lenses do not replace a run and are not needed where the question resolves in ten seconds); an explicit outcome for every finding (accepted / rejected and why; quietly dropping one is forbidden); stopping on a structural signal rather than an invented agreement score; reviewers write nothing — they only report. **The key caveat about grounding:** where there is no code there is nothing to check the reviewer against, so the gate's output there is material for the human, not a verdict of "clean", and the report says exactly that. **(1)** New `base/methodology/review-gate.md`. **(2)** `base/CLAUDE.md` — the file listed in the `methodology/` tree + an always-on paragraph "The independent review gate" in "How Claude works on tasks", right after "confirm understanding". **Downstream:** additive, no migration needed — maintenance installs the file and appends the paragraph; wiki knowledge untouched. The code mechanic is unchanged: its execution cycle builds on top of the shared gate (a re-review after the code is written, correctness through an actual run). Knowledge — ADR-0034 (gate calibration by risk).

## base@31
`[instruction]` **Re-grounding in the files after a context compaction + maintenance sees a lingering `tmp/`.** The far end of the `base@30` rule: a long pass now writes progress to disk, but at the moment the context runs out and the conversation is replaced by a summary, nobody uses that record — the model carries on from the summary, which has dropped exactly the operational detail (which item we stopped on, which unit of work is open, what was already rejected). Same class of failure as ADR-0036, except what breaks is the context rather than the process — and it fires more often: compaction arrives on its own, mid-work, unannounced. **(1)** `.claude/settings.json` — the `SessionStart` matcher widened from `startup|resume|clear` to `startup|resume|clear|compact`. **(2)** `.claude/hooks/freshness_check.py` — reads `source` from the payload on stdin (guarded by `isatty()` so a manual run doesn't block on a read that never ends) and, when `source == "compact"`, **always** injects a re-grounding note: lean on `STATE.md`, the open unit of work, and the run journal under `tmp/`; work recorded in the journal is not redone; if `tmp/` has subfolders, it names them. The note stacks with the existing overdue note when something is also overdue. ## software-engineering@6
`[instruction]` **Long-running operations: progress to disk, resumption instead of a restart, cleanup of temporary artifacts.** The mechanic described **how** code gets written and verified but said nothing about **how it survives an interruption** — a blind spot in the competence (no checkpoint/retry rule existed anywhere in the constructor, neither in `base` nor in the mechanics). Live incident: a long IO operation left running overnight, the machine fell asleep, **all** progress lost — the intermediate result had been piling up in the process's memory and vanished with it. A new "Long-running operations" section in `software-engineering.md` with an explicit tell for when it applies (a pass does not fit inside one stretch of human presence **or** a repeat pass is expensive — paid calls, long network IO, scraping) and six rules: (1) each item's/batch's result lands on disk immediately, an interruption at 90% leaves 90%; (2) a repeat launch **continues** via the journal and a stable item key, idempotently — "start from the top" does not count as a retry; (3) a failed item goes to the error journal and the run moves on, transient errors retried with a pause; (4) **the launch outlives the session** — a separate process, log to a file, the machine kept awake (macOS `caffeinate`), and the report names where the log is and what resumes it; (5) **resumption is verified in acceptance** by an interruption (an unverified checkpoint breaks precisely when it is needed); (6) **cleanup on completion** — temporary artifacts in `tmp/<operation>-<date>/` (not `output/`: results for the human live there), and once the result is accepted Claude offers cleanup as a list (what goes / what stays), deletion on confirmation, nothing removed before acceptance. Plus a hook into step 1 of the cycle: the statement for a long-running operation **must** name how progress is saved and how the run resumes, and the acceptance criteria must include an interruption check; otherwise the statement is not accepted. **Downstream:** a single-file swap of `methodology/software-engineering.md` at maintenance, no migration needed, wiki knowledge untouched. Knowledge — ADR-0036.

## software-engineering@5
`[instruction]` **Task-statement gate calibration: a cheap floor, a ceiling by surface, a narrowed trigger.** The gate's risk calibration had two tiers (routine `3+1` / strengthened "more verifiers") with no lower or upper bound. Three edits to step 2: **(1)** a lower tier added — **cosmetic / isolated additive → 2 lenses** (one correctness, one impact), not a minimum of `3+1`; **(2)** the strengthening is triggered by a **concrete flag** from the impact reviewer (irreversibility, silent data corruption, contract breakage), **not** by a task being "about deployment" (otherwise the strengthened path is the default for the whole sprint); **(3)** the number of reviews is tied to the **surface** (how many distinct modules/lenses actually need checking), not to repetition — the strengthening is bounded not by a number but by a ban on duplication/looping: if it doesn't converge in ~2 rounds → fix the statement/recon, don't add rounds. The gate header (step 2) reworded: "≥4" → "base composition 3+1, depth by risk". Reason — the live SPRINT-DEPLOY-PREP sprint: 148 subagents on a single task statement while calibration was already live, and a whole round (74/76 agents) fell on the session limit for nothing; quality comes from a diversity of lenses, not a count of copies. Knowledge — ADR-0034. Wiki knowledge untouched.

## software-engineering@4
`[instruction]` Against silent scope narrowing on "exhaustive" tasks ("the entire regulatory base", "all the integrations"). Three edits to the cycle: **(1)** step 1 (task statement) — a request that is exhaustive by nature must enumerate the full list of elements explicitly, not with a summarizing phrase (otherwise an exclusion is invisible both to the gate and to the human); **(2)** a new third case, **"Blocker inside scope"** (alongside "Gap inside scope" / "Blocker outside scope") — an element of the list that cannot be closed right now (typically: no test data to verify it against) does not slip silently into the backlog: first try to remove the cause yourself (construct representative data); if that fails — an explicit item in the report + the human's decision; the spec does not move to `completed` until every element has an outcome; **(3)** step 5 (report) — an outcome for every element of the list, not collapsed into a single backlog line. The reason: the agent decided on its own not to support the unverifiable part of the functionality and quietly shelved it as a "minor item" in STATE — silent corruption of the same rank (lost scope this time) as silent data corruption; both are symptoms of the same disease, "deciding without the human". Coordinated with `spec-lifecycle@5`. Knowledge — ADR-0028.
